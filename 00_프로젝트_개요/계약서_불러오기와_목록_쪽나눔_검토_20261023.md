## 1부. 계약서 불러오기 → 권리 정보 자동 생성 → 표준 계약 서명

### 1.1 요청

> 계약서(레이블 또는 권리자 계약별로 다를 수 있음)를 불러오면 권리 정보가 자동 생성되고, 권리 IR 생성에 필요한 정보가 누락되었으면 추가 입력하게 하고, 이후 이를 표준 계약서로 서명하도록 하는 방안

### 1.2 지금 구조([원천문서 설계](원천문서_관리와_권리·정책_입력·조회_설계_20261015.md) 4절)

| 길 | 하는 일 | 기록 상태 |
| --- | --- | --- |
| A. 자체 계약서 업로드 | PDF를 원천 문서로 올림 → 사람이 조항(쪽·인용·종류)을 표시 → 사람이 권리 주장 값을 입력하고 조항에 연결 → 상대 당사자 확인(14일) | 확인 전 `ASSERTED`, 확인 뒤 `VERIFIED` |
| B. 표준 계약 작성 | 템플릿 5종 v1 → 마법사 답 → 계약서 생성 → 전자서명 → 서명본이 원천 문서(`TEMPLATE_SIGNED`), 답이 그대로 동의·위임 기록 | 바로 `VERIFIED` |

- 두 길은 서로 이어지지 않는다. A에서 읽은 값을 B 마법사에 다시 넣어야 한다.
- 결정 **D2(2026-10-15)**: 자동 추출은 하지 않는다. 이유는 계약서를 외부 모델로 보내는 문제다. 요청을 받아들이면 이 결정을 다시 열어야 한다.
- 템플릿은 플랫폼 법무가 관리한다(D6). 테넌트 자체 템플릿과 역할은 상용 단계다(RD8).
- 표준 계약 마법사가 만드는 기록은 지금 동의·위임뿐이다. 녹음 권리·작가 지분·실연 주장은 원곡 권리 화면에서 직접 입력한다.

### 1.3 제안 흐름(A와 B를 하나로 잇는다)

```
① 계약서 불러오기 ── 원천 문서로 저장(원본 보존, 해시)
② 권리 정보 후보 만들기 ── 계약 유형별 "읽기 틀"이 조항을 찾아 값 후보를 채움
③ IR 필요 정보 대조 ── 이 곡의 IR에 필요한 항목 표에서 채워진 것 / 빠진 것 / 서로 다른 것을 표시
④ 빠진 것 입력 ── 사람이 채우고, 후보 값은 사람이 하나씩 확인(조항 위치가 함께 보임)
⑤ 표준 계약 만들기 ── ④의 값으로 표준 계약 템플릿을 미리 채움(원본 계약은 근거로 첨부)
⑥ 전자서명 ── 당사자 서명 → 서명본 원천 문서 + 권리 주장·위임·동의가 VERIFIED로 생성
```

- 원본 계약은 버리지 않는다. 표준 계약이 원본을 **대체하지 않고 확인·정리하는 계약**이 되며, 조항에 원본 문서를 근거로 적는다.
- ②의 "자동"은 방식에 따라 범위가 크게 달라진다. 1.5의 CT1에서 정한다.
- ⑥ 뒤에는 상대 당사자 확인(14일)이 필요 없다. 모두 서명했기 때문이다. 길 B의 장점을 그대로 쓴다.

### 1.4 IR 생성에 필요한 정보(③의 대조 표)

| 묶음 | 항목 | 지금 입력하는 곳 | 표준 계약으로 만들 수 있나 |
| --- | --- | --- | --- |
| 작품 | 곡명, 작가, 작가별 지분(bps, 합 100%), 작품 이용 범위 | 원곡 권리 › 작품 | 작품 이용허락 템플릿에 작가 지분 변수 추가 필요 |
| 녹음 | 녹음, 마스터 보유자, 녹음 이용 범위 | 원곡 권리 › 녹음 | 녹음 이용허락(이용 범위만), 보유자 주장은 추가 필요 |
| 실연 | 슬롯·파트별 원곡 담당 멤버, 보이스 소유, 스템 실연 | 원곡 권리 › 실연, 스템 | 템플릿 없음. 실연자 앱 확인으로 처리 중 |
| 수령 위임 | 멤버 → 소속사, 비율, 기간 | 문서·계약(표준 계약) | 있음(수령 위임계약 v1) |
| 이용 동의 | 멤버 팬앱 이용 동의 | 실연자 앱 | 있음(멤버 본인) |
| 근거 | 각 주장의 원천 문서·조항 | 원천 문서 | 서명본이 자동 근거 |

빠진 것이 남아 있으면 ⑤로 넘어가지 않는다. 정합성 규칙(지분 합계, 근거 문서, 마스터 보유자 ↔ 녹음 주장 등)을 ③에서 미리 돌려 보여 준다.

### 1.5 정할 것

- [x] **CT1 ②의 "자동" 방식** — D2를 다시 연다
  - 가. 외부 AI 모델로 추출: 계약서를 모델 공급자로 보낸다. 범위는 가장 넓다. 계약서 외부 반출 동의와 처리 위탁 계약이 필요하다.
  - 나. 플랫폼 안에서 돌리는 모델(자체 호스팅)로 추출: 반출은 없다. 품질과 운영 비용 부담이 있다.
  - 다. **계약 유형별 읽기 틀(양식 대응)**: 레이블·권리자마다 쓰는 계약 양식을 한 번 등록해 "몇 조 몇 항 = 작가 지분" 같은 위치를 정해 두면, 같은 양식의 계약은 값이 자동으로 채워진다. 처음 보는 양식은 사람이 조항을 표시한다(지금 길 A). 반출이 없고 MVP 범위에 맞는다.
  - 제안: **다**로 시작하고, 가·나는 D2 재결정 때 검토한다.
  - 결정(2026-10-23): 제안대로 — 다(계약 양식별 읽기 틀). 외부 반출 없음. 가·나는 상용 단계에서 다시 본다
- [x] **CT2 "계약별로 다른" 양식 관리** — 읽기 틀을 누가 등록하나
  - 제안: 테넌트(빅히트)가 자기 양식의 읽기 틀을 등록하고, 플랫폼이 승인한다. 템플릿(표준 계약)은 계속 플랫폼 법무가 관리한다.
  - 결정(2026-10-23): 제안대로
  - 이것은 테넌트 자체 템플릿(RD8, 상용 단계)과 다르다. 읽기 틀은 값을 읽는 위치일 뿐, 계약서를 만드는 데 쓰지 않는다.
- [x] **CT3 표준 계약의 성격** — 원본을 확인·정리하는 계약(원본 유지)인가, 원본을 대체하는 계약인가
  - 제안: 확인·정리 계약. 대체 계약은 법무 검토가 필요하다.
  - 결정(2026-10-23): 제안대로 — 원본 유지, 표준 계약은 확인·정리
- [x] **CT4 누가 다시 서명하나** — 원본 당사자 전원인가, 바뀐 권리의 당사자만인가
  - 예: 위탁 작가(플랫폼 밖)는 지금도 운영 원문 대조로 확인한다.
  - 제안: 표준 계약 템플릿의 서명자 규칙을 그대로 쓴다. 위탁 작가는 지금처럼 운영 대조로 확인한다.
  - 결정(2026-10-23): 제안대로
- [x] **CT5 표준 계약이 "권리 귀속·지분"까지 확정하게 할지**
  - 지금 템플릿 5종이 서명 뒤 만드는 기록은 **이용 허락(동의)과 수령 위임뿐**이다.

    | 템플릿 | 받는 값 | 서명 뒤 만드는 기록 |
    | --- | --- | --- |
    | 녹음 이용허락 v1 | 허락자, 녹음, 이용 범위·기간 | 녹음 이용 동의 |
    | 작품 이용허락 v1 | 허락자, 이용 범위·기간 | 작품 이용 동의 |
    | 실연 이용 동의서 v1 | 실연자, 보이스, 이용 범위·기간 | 실연 이용 동의 |
    | 실연 수익 수령 위임계약 v1 | 실연자, 소속사, 비율, 기간 | 수령 위임 |
    | 플랫폼 이용계약 v1 | 보유자, 기간 | 없음 |

  - IR 정산의 바탕인 **"누가 권리자이고 몇 %인가"**(권리 주장)는 어느 템플릿에도 없다.
    - 마스터 보유자, 작가별 지분(bps), 보이스 소유, 슬롯·파트별 실연 담당이 여기에 해당한다.
    - 이 값들은 원곡 권리 화면에서 직접 입력한다(`ASSERTED`). 그 뒤 상대 당사자 확인(14일)을 따로 거쳐 `VERIFIED`가 된다.
    - 그래서 1.3의 흐름대로 계약서를 불러와 표준 계약에 서명해도, 이용 허락만 확정되고 지분은 여전히 확인 대기로 남는다.
  - 선택지
    - 가. **기존 템플릿 v2에 변수 추가**
      - 작품 이용허락에 작가·지분 표, 녹음 이용허락에 마스터 보유 선언, 실연 동의서에 담당 파트를 넣는다.
      - 템플릿 3종을 개정해야 한다. "허락"과 "귀속·지분"이라는 성격이 다른 조항이 한 계약에 섞인다.
    - 나. **새 템플릿 "권리 확인서" 1종 추가**
      - 곡 하나의 권리 주장(마스터 보유자, 작가별 지분)을 표로 담는다.
      - 해당 권리자가 서명하면 그 주장이 서명본을 근거로 바로 `VERIFIED`가 된다.
      - 기존 5종은 그대로 둔다.
      - CT3의 "원본을 확인·정리하는 계약"이 바로 이 문서다.
    - 다. **확장하지 않음**: 지분은 지금처럼 화면 입력과 상대 확인으로 처리하고, 표준 계약은 허락·위임만 다룬다.
  - 제안: **나. 권리 확인서**
    - 서명자 묶음
      - 레이블용(마스터 보유): 레이블이 서명한다.
      - 작가용(작가 지분 표 전체): 작가 전원이 서명한다. 지분은 작가끼리 맞물리므로 한 부로 한다. 위탁 작가는 CT4대로 운영이 원문을 대조한다.
      - 멤버(보이스 소유·파트 담당): 지금처럼 실연자 앱 확인으로 둔다.
    - 원본 계약은 확인서 조항에 근거로 적는다.
    - 읽기 틀(CT1)이 채운 값이 그대로 확인서 변수가 된다.
    - 서명하면 상대 확인 14일 대기가 없어진다.
    - 새 기록 종류 `CLAIM_CONFIRM`(권리 주장 생성·확정)을 더해야 한다. 템플릿 v1 작성 ≠ 승인 절차를 따른다.
  - 결정(2026-10-23): 제안대로 — 나. 권리 확인서(레이블용·작가용), 멤버는 실연자 앱 확인 유지

## 2부. 목록 쪽 나눔(10행) — API 점검

### 2.1 규칙(디자인 가이드 5절, 2026-10-23)

- 모든 목록 표는 10행 단위로 나누고, 표 아래에 `1–10 / N` · `‹ 1 2 ›`를 둔다.
- 한 쪽뿐이어도 줄을 둔다.
- 항목 수가 정해진 표(확인 항목, 규칙별 결과)에는 두지 않는다.

### 2.2 지금 API(rights-core, `feat/works-ui` 기준)

- 공통 헬퍼 `platform/paging.ts`는 커서 방식이다.
  - 요청: `?limit=`(기본 50, 최대 200), `?after=`
  - 응답: `{items, next}`
  - **전체 건수를 주는 목록은 하나도 없다.** 그래서 지금 방식으로는 `N`과 쪽 번호를 그릴 수 없다.
- 페이징이 없는데 계속 늘어나는 목록:
  - LIMIT도 없음: `/confirmations`, `/consents`, `/contracts`, `/documents`, `/validation-issues`, `/tenants`, `/links`, `/parties/:id/statements`, `/audio/queue`, `/traffic-pools`, `/hub/assets`, `/exposure-holds`, `/trust/works`, `/asset-mappings`
  - LIMIT에서 말없이 잘림: `/works/overview`(500, 작품 목록 화면이 기대는 API), `/scopes`(500)
- 페이징 API를 화면이 첫 쪽만 보는 곳:
  - `/users`(담당자 계정), `/parties`, `/packs`
  - `/issues`: 작품 목록에서 `?pack=` 없이 200건을 받아 화면에서 거른다
- 화면은 "더 보기"(무한 스크롤)이거나 전부 모아 보는 방식(`useAll`)이다. 10행 쪽 번호 방식과 다르다.

### 2.3 제안

- [ ] **PG1 목록 API에 쪽 번호 방식 추가**
  - 요청 `?page=1&size=10`(size 최대 100), 응답 `{items, page, size, total}`
  - 공통 헬퍼 `parsePageNo`·`pageResult`를 두고, `COUNT(*) OVER()`나 별도 count로 total을 낸다
  - 기존 커서 API는 정산·원장처럼 큰 목록에 그대로 둔다
- [ ] **PG2 먼저 고칠 API**(운영 관리·작품 목록 화면이 쓰는 것)
  - `/works/overview`, `/confirmations`, `/consents`, `/contracts`, `/documents`, `/validation-issues`, `/issues`(+ `?pack=`), `/parties/:id/statements`, `/users`
  - 필터(곡·상태·검색)를 서버로 옮긴다. 지금은 전부 받아 화면에서 거른다
- [ ] **PG3 곡 단위 작은 목록**(한 곡의 계약·동의·스템 오디오·템플릿)
  - 응답 전체를 받아 화면에서 10행씩 나눈다. 서버는 그대로 둔다
- [ ] **PG4 백오피스 공통 표 쪽 나눔 컴포넌트**
  - 시안 모양: 32px 버튼, 지금 쪽 `#1d4ed8`
  - 지금 쓰는 `Pager`("더 보기")와 `useAll`을 이것으로 바꾼다

### 1.7 구현 뒤 결정(2026-10-23, 3부-B 보고)
