# 원천 문서 관리와 권리·정책 입력·조회 설계

- 작성일: 2026-10-15 (설계 초안, 미구현)
- 관련 문서: [시스템 아키텍처 및 업무 분리안](시스템_아키텍처_및_업무분리안_20261012.md), `03_dobedupop_플랫폼설계/최신설계/데이터모델_v2.8.md`(3.3 권리 주장, 정책 폼→MDRL 텍스트), `백오피스_IA_와이어프레임_Userflow.md`(표준 계약 관리, 동의 계약서 열람)

facts IR과 정책 IR은 정산 엔진이 읽는 형식이라 권리자가 읽거나 직접 쓰기 어렵다. 이 문서는 사람이 다루는 것(계약서와 입력 화면)과 기계가 다루는 것(봉인 IR)을 나누고, 그 사이를 근거 연결로 잇는 설계를 제안한다. 문서와 기록이 서로 맞는지(누락·의존성·연관성)를 검증하고 고칠 때까지 추적하는 절차도 함께 다룬다(6절).

## 1. 지금 상태

| 항목 | 지금 | 문제 |
| --- | --- | --- |
| 권리 사실(facts) | 운영 백오피스에서 주장·위임을 한 행씩 폼으로 입력 | 계약서 한 장에서 나오는 주장 여러 개를 따로 입력한다. 무엇을 근거로 입력했는지 남지 않는다 |
| 증빙 | 주장의 "증빙 digest", 동의의 "계약서 URI", 위임의 "출처 참조"를 문자열로 직접 입력 | 원문을 올리고 보관하는 곳이 없다. digest를 사람이 계산해 넣어야 한다 |
| 정책 | MDRL 텍스트를 편집창에 직접 작성해 컴파일 | 권리자가 쓸 수 없다. 데이터모델 v2.8의 "폼 → MDRL 텍스트 생성"은 아직 구현되지 않았다 |
| 조회 | 봉인 digest, IR JSON, MDRL 텍스트 | 일반 사용자는 "그래서 누가 얼마를 받는가"를 알 수 없다 |

엔진 쪽 바탕은 이미 있다. 권리 주장의 증빙 digest는 facts IR(`claim.evidence`)에 들어가 봉인되고, 공개본에서는 커밋먼트로 가려진다. 따라서 원문 저장소만 붙이면 봉인된 facts가 원문을 가리키게 된다.

## 2. 원칙

1. **세 층을 나눈다.**

   | 층 | 무엇 | 누가 다루나 |
   | --- | --- | --- |
   | 원천 문서 | 계약서·동의서·위임장·증빙 원문(PDF·스캔·서명본) | 사람이 올리고 읽는다 |
   | 구조화 기록 | 주장·위임·동의·정책 폼 값(행) | 사람이 입력·확인한다. 편집 단위다 |
   | 봉인 IR | facts·정책 IR(JSON, digest) | 시스템만 만든다. 사람에게는 "봉인됨" 배지와 사람이 읽는 요약으로만 보여 준다 |

2. **모든 구조화 기록은 근거를 가리킨다.** 기록마다 원천 문서와 그 안의 조항(페이지·인용)을 연결한다. 근거가 없는 기록은 `ASSERTED`로만 저장된다.
3. **플랫폼은 권리를 정하지 않는다.** 조항 표시와 값 입력은 사람이 한다(자동 추출은 하지 않는다, D2). 기록을 확정하는 것은 권리자이고, 상대 당사자 확인 또는 플랫폼 확인(KYB·계약 대조)을 거쳐 `VERIFIED`가 된다.
4. **원문은 불변이고 내용 주소로 가리킨다.** 원문을 고치면 새 문서 버전이 된다. 이전 기록은 이전 digest를 계속 가리키므로, 이미 봉인된 정책·발행의 근거는 바뀌지 않는다. 봉인 IR에는 원문이 아니라 digest만 들어간다.

## 3. 데이터 모델 추가

```
[source_document] 1 ──< [document_clause] 1 ──< [record_evidence] >── right_claim | mandate | consent_agreement | policy_version
       │ supersedes(이전 버전)
       └── file: 오브젝트 저장소(암호화), sha256
```

**source_document** (`doc_`): 원천 문서 한 건(한 버전).

| 컬럼 | 설명 |
| --- | --- |
| `document_id`, `version`, `supersedes` | 문서와 버전 사슬. 원문을 바꾸면 새 버전 |
| `owner_tenant_id` | 올린 테넌트(RLS) |
| `kind` | `MASTER_CONTRACT`(녹음)·`PUBLISHING`(작품)·`PERFORMER_CONSENT`(실연 동의)·`MANDATE`(위임·전속)·`PLATFORM_CONTRACT`·`EVIDENCE`(기타 증빙) |
| `title`, `parties[]`, `effective_from`·`effective_to` | 사람이 붙이는 색인 정보 |
| `file_sha256`, `byte_size`, `mime`, `page_count`, `storage_uri` | 원문 파일. digest가 봉인에 들어가는 값이다 |
| `origin` | `UPLOADED`(자체 계약서) · `TEMPLATE_SIGNED`(표준 계약 마법사로 만들고 서명) · `IMPORTED`(일괄 등록) |
| `status` | `UPLOADED → IN_REVIEW → CONFIRMED`, 또는 `REJECTED` |
| `confidentiality` | 열람 범위(소유 테넌트·당사자·플랫폼). 금액 조항 마스킹 여부 |

**document_clause**: 문서 안의 근거 조항. 페이지 번호, 영역(좌표) 또는 인용문, 조항 종류(지분·위임·이용 범위·기간·분배율), 읽어 낸 값(JSON), 표시한 사람과 시각.

**validation_issue**: 문서·기록 정합성 검증에서 찾은 문제와 그 처리 이력(6.4).

**record_evidence**: 구조화 기록과 조항의 연결(다대다). 계약서 한 장이 주장 여러 개의 근거가 되고, 주장 하나가 여러 문서(예: 계약서 + 부속 합의서)를 근거로 가질 수 있다.

**기존 컬럼의 정리.**

| 기존 | 바뀌는 점 |
| --- | --- |
| `right_claim.evidence_digest` | 직접 입력하지 않는다. 근거 문서를 연결하면 시스템이 채운다: 문서 하나면 그 원문의 SHA-256, 여러 개면 정렬한 원문 해시 JSON 배열의 SHA-256(둘 다 `mdrl:sha256:<hex>`). 그대로 facts IR `evidence`로 봉인된다 |
| `consent_agreement.source_contract_uri` | `source_document` 참조로 바꾼다 |
| `mandate.source_ref` | 근거 연결로 바꾼다. `mandate.evidence_digest`를 더해 주장과 같이 facts `evidence`로 봉인한다(결정 D4, MDRL facts mandate의 선택 필드 `evidence`) |
| `policy_version` | 정책의 근거(플랫폼 계약·권리자 합의서)를 연결한다. 정책 IR에는 넣지 않는다(정책의 근거는 승인 서명이다) |

## 4. 입력 흐름

### A. 자체 계약서가 있을 때 (업로드)

1. **문서함에 올린다.** 끌어다 놓기로 올리고, 종류·당사자·기간을 고른다. 같은 파일(같은 해시)은 다시 올라가지 않는다.
2. **조항을 표시한다.** 분할 화면 왼쪽에 원문, 오른쪽에 입력 폼이 있다. 원문에서 문장을 끌어 선택하면 조항이 되고, 폼의 필드에 연결된다.
3. **기록을 만든다.** 한 문서에서 나온 기록(예: 녹음 100% 주장, 작가 2명 50%씩, 멤버 7명 → 소속사 위임)을 한 화면에서 함께 저장한다. 저장 직후 상태는 `ASSERTED`다.
4. **확인한다.** 상대 당사자(예: 작가)에게 "이 계약서의 이 조항으로 이렇게 등록됐다" 확인 요청이 간다. 상대가 확인하거나 플랫폼이 계약 대조를 마치면 `VERIFIED`가 된다. 이의가 있으면 분쟁으로 넘어간다(기존 분쟁 흐름).

```
┌─ 원천 문서: 빅히트-멤버 전속계약서 v2 (12쪽) ─────────┬─ 이 문서에서 만든 기록 ─────────────────────────┐
│  p.4  제7조(실연 수익의 수령)                            │ ① 위임  정국 → 빅히트 뮤직(소속사) · 실연 · 100%   │
│  ┌───────────────────────────────────────────────┐ │    근거: p.4 제7조 1항  ● 확인됨(정국)             │
│  │ 을은 본 계약 기간 중 발생하는 실연 관련 수익의  │ │ ② 위임  지민 → 빅히트 뮤직(소속사) · 실연 · 100%   │
│  │ 수령을 갑에게 위임한다. ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓      │─┼─▶  근거: p.4 제7조 1항  ◐ 확인 대기             │
│  └───────────────────────────────────────────────┘ │ ③ 기간  2025-01-01 ~ 2027-12-31  근거: p.2 제3조    │
│  [조항 선택]                                             │ [기록 추가]  [모두 저장(ASSERTED)]  [확인 요청]    │
└──────────────────────────────────────────────────────┴────────────────────────────────────────────────┘
```

### B. 계약서가 없을 때 (최초 작성)

자체 계약서 없이 플랫폼에서 처음 권리를 정하는 경우(예: 팬앱 전용 2차 이용 허락)는 표준 계약 템플릿으로 작성한다.

1. **질문형 마법사.** "이 곡의 녹음 권리자는?", "작품 지분은?", "멤버 실연 몫은 누가 받나(본인/소속사)?", "허락 범위는(지역·매체·기간)?"을 차례로 묻는다. 답은 처음부터 구조화 값이다.
2. **사람이 읽는 계약서 미리보기.** 답으로 표준 계약서 문안을 채워 보여 준다(법무가 관리하는 템플릿 버전).
3. **전자서명.** 당사자가 서명하면 서명본 PDF가 원천 문서(`TEMPLATE_SIGNED`)가 되고, 마법사 답이 그대로 주장·위임·동의 기록이 된다. 조항과 값이 템플릿에서 이미 대응되므로 추출이 필요 없고, 모든 당사자가 서명했으므로 바로 `VERIFIED`다.

실연자 앱의 동의 서명도 같은 방식이다. 지금은 범위 값만 저장하지만, 서명 시 동의서 문안(PDF)을 원천 문서로 남기면 IA의 "체결된 동의 계약서 원문 열람"이 된다.

### C. 분배 규칙(정책)

권리자는 MDRL을 쓰지 않는다. 폼으로 작성하고, 시스템이 MDRL 텍스트를 만들어 컴파일한다(데이터모델 v2.8의 폼 → `policy_version.source_text` 흐름).

```
┌─ 분배 규칙: Dynamite 팬앱 전용 (v2 초안) ───────────────────────────────────────────────┐
│ 1차 분할   플랫폼 [25]%   운영 [5]%   권리자 [70]%          (플랫폼 계약 허용 구간: 권리자 65~75%) │
│ 2차 분할   녹음 [40]%   실연 [45]%   작품 [15]%                                            │
│ 실연 몫    ◉ 참여 멤버 고정 40% + 부른 시간 60%   ○ 부른 시간만   1인 상한 [50]%            │
│            ☑ 위임이 있으면 위임받은 쪽이 받는다                                            │
│ ── 이렇게 나뉩니다(구매 3,300원 1건, 원곡 배치 조합) ───────────────────────────────────── │
│ 플랫폼 825 · 운영 165 · 빅히트(레이블) 924 · 빅히트(소속사) 1,040 · 작가 2명 173씩          │
│ ── 쉬운 말로 ───────────────────────────────────────────────────────────────────────────── │
│ "매출의 70%가 권리자 몫이고, 그중 40%는 녹음 권리자에게, 45%는 그 조합을 부른 멤버에게…"  │
│ [MDRL 텍스트 보기(고급)]  [이전 버전과 비교]  [저장 → 컴파일 → 승인 요청]                  │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

- **예시 계산은 엔진이 한다.** 화면에서 따로 계산하지 않는다. 현재 facts와 대표 조합으로 엔진 시뮬레이션을 돌린 결과다(봉인하지 않음). Dynamite 예시의 "구매 1건 계산" 표와 같은 방식이다.
- **허용 구간을 미리 막는다.** 플랫폼 계약·계승 규칙(하한·상한)을 넘는 값은 입력 단계에서 막는다. 컴파일 진단은 마지막 방어선이다.
- **고급 모드.** MDRL 텍스트를 직접 고치는 화면은 운영·고급 사용자에게만 열어 둔다. 직접 고친 정책은 폼으로 되돌릴 수 없다는 표시를 한다.

### D. 일괄 등록

카탈로그가 큰 권리자는 크레딧 시트(CSV·스프레드시트)를 올린다. 행마다 원천 문서를 지정하고, 연동 허브처럼 줄별 결과(적용·거부 사유)를 보여 준다.

## 5. 조회: 사람이 읽는 보기

봉인 IR을 그대로 보여 주지 않는다. 같은 행에서 사람이 읽는 보기를 만들고, 봉인과 일치하는지만 배지로 알린다.

| 보기 | 내용 |
| --- | --- |
| **권리 요약** | 문장으로 보여 준다. 예: "녹음: 빅히트 뮤직(레이블) 100%", "작품: David Stewart 50%, Jessica Agombar 50%", "실연: 멤버 7명, 실연 몫은 빅히트 뮤직(소속사)이 받음(위임)". 문장마다 근거 문서·쪽으로 가는 링크가 있다 |
| **권리 지도** | 곡 → 녹음·작품 → 스템·보이스 → 권리자 → 위임받은 쪽을 그래프로 보여 준다. 분쟁 중인 연결은 표시한다 |
| **정책 설명** | 쉬운 말 설명과 예시 계산표, 이전 버전과 바뀐 점("실연 1인 상한 60% → 50%") |
| **봉인 상태 배지** | "봉인됨 2026-02-01 · 서명 3/3(편집·승인·활성화) · 원문 일치 ✓". digest와 JSON은 "개발자 보기"에 접어 둔다 |
| **근거 추적** | 정산 라인 → 발행 봉인 → 권리 주장 → 근거 조항 → 원문 쪽. ⑧ "한 건 추적"을 원문까지 늘린 것이다 |

역할에 따라 보이는 범위가 다르다.

| 누구 | 보이는 것 |
| --- | --- |
| 권리자(소유 테넌트) | 자기가 올린 문서 전체, 자기 곡의 요약·지도·정책 |
| 상대 당사자 | 자기와 관련된 조항과 기록(예: 작가는 작품 지분 조항). 다른 당사자의 금액 조항은 가린다 |
| 실연자 앱 | 내 동의서 원문, 나를 가리키는 주장과 그 근거 조항(이의제기 화면에서 함께 보인다) |
| 플랫폼 운영 | 전부 보되 원문 열람은 열람 기록에 남고(조회 통제 1단계), 금액 조항은 기본 마스킹(2단계) |

## 6. 정합성 검증과 수정·보완

문서와 기록은 따로 들어오고, 서로 기대고 있다. 녹음 계약·퍼블리싱 계약·전속계약·실연 동의·플랫폼 계약·분배 규칙이 서로 맞아야 정산이 맞는다. 그래서 하나씩 저장할 때의 형식 검사와 별도로, **곡 단위로 문서와 기록을 함께 보는 검증**을 두고, 찾은 문제를 고칠 때까지 추적한다.

### 6.1 무엇을 검사하나

검사는 세 종류다.

**누락(빠진 것).** 곡 하나가 정산 가능하려면 있어야 하는 근거와 기록이다.

| 규칙 | 검사 | 지금 |
| --- | --- | --- |
| 필수 근거 문서 | 녹음 주장에 녹음 계약, 작품 주장에 퍼블리싱 계약(또는 작가별 계약), 실연 주장·위임에 실연 동의·전속계약이 연결돼 있다 | 신규(`DOC_EVIDENCE_MISSING`) |
| 스템·보이스 연결 | 권리 대상 스템마다 실연 주장(`PERFORMED_BY`), 보이스마다 소유 주장(`OWNED_BY`)이 있다 | 엔진 `FACTS_PATH_MISSING` |
| 지분 합 | 같은 대상·역할의 지분 합이 100%다 | 엔진 `FACTS_SUM_MISMATCH` |
| 청구권자 커버리지 | 팩에 선언된 권리자와 facts에서 나온 권리자가 같다 | 엔진 `FACTS_UNCOVERED_CLAIMANT`·`FACTS_CLAIMANT_DRIFT` |
| 정책 커버리지 | 분배 규칙이 facts의 모든 권리자 역할을 다룬다 | 엔진 `ALLOC_UNCOVERED_CLAIMANT` |
| 동의 커버리지 | 팩의 이용 범위에 필요한 동의(작품·녹음·쓰인 보이스)가 모두 있다 | 발행 게이트 `ISSUE_NOT_LICENSED`(사후). 활성화 전에 미리 알리는 검사는 신규(`DOC_CONSENT_MISSING`) |
| 지급 정보 | 정산 대상 권리자에게 지급 프로필(계좌·세무 유형)이 있다 | 지급 보류(사후). 미리 알리는 검사는 신규(`DOC_PAYOUT_PROFILE_MISSING`) |

**의존성(두 문서의 항목·기준이 맞는가).** 같은 항목이 두 문서에 있으면 값이 같아야 하고, 상위 문서가 정한 범위 안에서 하위 문서가 정해져야 한다.

| 규칙 | 상위(기준) 문서 → 하위 문서 | 검사 |
| --- | --- | --- |
| 같은 항목 일치 | 퍼블리싱 계약 ↔ 작가 개별 계약 | 작품 지분·작가 목록이 같다(`DOC_VALUE_CONFLICT`) |
| 당사자 일치 | 문서 당사자 ↔ 기록의 파티 | 기록의 권리자가 근거 문서의 당사자다. 서명자가 법인 대표·대리 권한을 가진다(`DOC_PARTY_MISMATCH`) |
| 대상 일치 | 문서의 곡명·ISRC·녹음 버전 ↔ 등록된 작품·녹음 | 다른 곡의 계약을 근거로 연결하지 않았다(`DOC_SUBJECT_MISMATCH`) |
| 범위 포함 | 플랫폼 계약 ⊇ 분배 규칙 1차 분할 | 권리자 풀·수수료가 계약 허용 구간 안이다(계승 규칙 `INHERITANCE_VIOLATION`, 정책 폼에서 입력 단계 차단) |
| 범위 포함 | 원천 동의(T0) ⊇ 팩 이용 범위 | 행위·지역·매체·청중·기간이 동의 범위 안이다(엔진 `GRANT_SCOPE_WIDENING`) |
| 범위 포함 | 전속계약의 위임 범위 ⊇ 소속사가 대신 한 일 | 소속사가 멤버 대신 서명·수령하는 권한이 계약 범위 안이다(`DOC_AUTHORITY_EXCEEDED`) |
| 기간 정합 | 동의·위임·계약 기간 ⊇ 팩 운영·정책 활성 기간 | 기간이 끝나기 전에 팩이 계속 열려 있지 않다. 공백·겹침이 없다(`DOC_PERIOD_GAP`) |

**연관성(바뀐 것이 어디에 닿나).** 문서가 개정·해지·만료되거나 기록이 바뀌면, 그것에 기대는 것을 다시 검사한다. 역방향 의존성(문서 → 조항 → 기록 → facts 봉인 → 정책 → 팩 → 발행 조합 → 매출 → 정산 라인)을 따라간다. ⑧ 영향 분석과 같은 경로이고, 시작점에 "문서"가 추가된다.

| 사건 | 다시 검사하는 것 |
| --- | --- |
| 문서 새 버전 | 그 문서를 근거로 한 기록. 값이 달라졌으면 기록 수정 이슈를 만든다 |
| 문서 해지·만료 | 그 문서에 기대는 기록·동의·위임, 그 곡의 팩. 동의 철회와 같이 노출·발행에 반영할지 판단 이슈를 만든다 |
| 만료 임박(30일) | 갱신 요청 이슈(경고) |
| 기록 수정 | 같은 곡의 지분 합·커버리지, 활성 정책의 재고정 필요 여부 |

### 6.2 언제 검사하나

| 시점 | 무엇을 | 결과 |
| --- | --- | --- |
| 문서 등록·조항 연결 | 그 문서와 연결된 기록 | 화면에 즉시 표시(저장은 막지 않는다) |
| 기록 저장 | 같은 곡의 누락·의존성 규칙 | 이슈 생성·갱신 |
| 정책 컴파일 | 엔진 진단 + 문서 규칙 | 차단 이슈가 있으면 컴파일 결과에 함께 표시 |
| 정책 활성화·팩 활성화 | 차단(BLOCK) 이슈 전부 | 열린 차단 이슈가 있으면 거부(`ACTIVATION_BLOCKED` 진단에 이슈 목록 포함) |
| 매일 정기 검사 | 기간·만료·지급 정보 | 경고 이슈 |
| 문서 개정·해지 | 연관성 규칙 | 영향받는 기록·팩에 이슈 |

발행 게이트에는 이 검증을 넣지 않는다. 발행 게이트는 이미 동의·분쟁·스템 상태를 보고, 문서 정합성은 활성화 단계에서 막는 것으로 충분하다(활성화된 팩은 검증을 통과한 상태다).

### 6.3 심각도

| 등급 | 뜻 | 예 |
| --- | --- | --- |
| BLOCK | 고치기 전에는 정책·팩을 활성화할 수 없다. 위험 수용도 불가 | 지분 합 불일치, 필수 근거 문서 없음, 동의 범위 초과, 당사자 불일치 |
| WARN | 활성화는 되지만 기한 안에 고쳐야 한다. 기한이 지나면 BLOCK으로 오른다 | 30일 안 만료, 지급 정보 없음, 작가 개별 계약 미첨부(퍼블리싱 계약은 있음) |
| INFO | 참고 | 스캔 품질 낮음, 쪽 수가 문서 정보와 다름 |

### 6.4 수정·보완 프로세스

찾은 문제는 **검증 이슈**로 남기고, 고칠 때까지 추적한다.

```
 탐지 ──▶ OPEN ──▶ 담당 배정 ──▶ 조치 ──▶ 재검증 ──▶ RESOLVED(자동)
                                   │           └── 여전히 위반 → OPEN 유지
                                   ├─ 위험 수용(WARN만, 플랫폼 승인·사유·기한) → ACCEPTED
                                   └─ 오탐 표시(플랫폼 승인·사유) → DISMISSED
```

**validation_issue** (`vis_`): 규칙 코드, 심각도, 대상(곡·문서·기록·정책·팩), 관련된 두 쪽(예: 퍼블리싱 계약 p.3 제5조 ↔ 작가 계약 p.2 제2조), 설명, 고치는 방법, 담당, 기한, 상태(`OPEN | RESOLVED | ACCEPTED | DISMISSED`), 처리 이력. 같은 규칙·같은 대상의 이슈는 하나만 열린다(재검사 때 갱신).

**담당.** 기본은 곡을 소유한 테넌트다. 고칠 것이 상대 당사자의 문서이면 그 당사자에게 요청이 간다(예: 작가에게 개별 계약 업로드 요청). 플랫폼은 조치하지 않고 배정·독촉·위험 수용 승인만 한다.

**조치 유형.**

| 조치 | 언제 | 결과 |
| --- | --- | --- |
| 기록 수정 | 입력 실수(지분 오타, 잘못된 파티) | 새 버전 기록(추가 전용). 근거 조항 연결은 다시 확인 |
| 문서 보완 요청 | 근거 누락, 만료 임박 | 당사자에게 업로드·갱신 요청. 올라오면 연결 후 재검증 |
| 확인 요청 | 값은 맞아 보이나 상대 확인이 없다 | 상대 당사자 확인 → `VERIFIED` |
| 분쟁 개시 | 두 문서가 다르고 당사자 간 주장이 엇갈린다 | 기존 분쟁 흐름(팩 일시정지, 분쟁 종결 후 재고정) |
| 위험 수용 | WARN이고 당장 고칠 수 없다 | 플랫폼 승인, 사유·기한 기록. 기한이 지나면 다시 OPEN |

**재검증과 종결.** 조치가 저장되면 그 이슈의 규칙을 바로 다시 돌린다. 위반이 없으면 시스템이 `RESOLVED`로 닫는다(사람이 닫지 않는다). 그래서 "고쳤다고 표시했는데 실제로는 안 고쳐진" 상태가 생기지 않는다.

### 6.5 화면

권리자 포털 곡 화면에 **정합성 점검** 탭을 둔다. 아래는 Dynamite에 가상의 문제 세 건을 넣은 예시 화면이다.

```
┌─ Dynamite · 정합성 점검 ─────────────────────────── 차단 1 · 경고 2 · 통과 14 ─┐
│ 필수 근거   녹음 계약 ✓   퍼블리싱 계약 ✓   전속계약 7/7 ✓   실연 동의 6/7 ✗     │
│ 지분 합     녹음 100% ✓   작품 100% ✓   실연(스템 49개) ✓                        │
│ 커버리지    팩 권리자 11 = facts 권리자 11 ✓   분배 규칙이 모든 역할을 다룸 ✓      │
│ ───────────────────────────────────────────────────────────────────────────── │
│ ⛔ DOC_EVIDENCE_MISSING  슈가 실연 동의서 없음 (담당: 빅히트 뮤직 · 기한 10/22)   │
│    [슈가에게 동의 요청]  [동의서 업로드]                                          │
│ ⚠ DOC_VALUE_CONFLICT   작품 지분: 퍼블리싱 계약 50:50 ↔ J. Agombar 계약 45:55     │
│    [두 조항 나란히 보기]  [기록 수정]  [작가에게 확인 요청]  [분쟁 개시]           │
│ ⚠ DOC_PERIOD_GAP       실연 동의 종료 2027-01-01 < 팩 운영 종료 2027-06-30         │
│    [동의 갱신 요청]  [팩 종료일 조정]                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **나란히 보기.** 의존성 이슈는 두 문서의 해당 조항을 좌우로 띄워 차이를 강조한다.
- **운영 쪽.** 운영 백오피스는 전 테넌트의 이슈를 큐로 본다(차단 이슈 수, 기한 초과, 담당별). ⑧ "권리 등록" 단계에 신호로 붙인다.
- **실연자 앱.** 나에게 온 확인·보완 요청(동의서 업로드, 위임 확인)을 알림과 할 일로 보여 준다.

### 6.6 규칙 관리

- **규칙 카탈로그.** 규칙은 코드로 정의한다(규칙 코드, 대상, 검사, 심각도, 고치는 방법 문구). 엔진 진단(`FACTS_*`·`ALLOC_*`·`GRANT_*`)은 그대로 이슈로 옮기고, 문서 층 규칙(`DOC_*`)만 새로 만든다. 같은 문제를 두 곳에서 따로 검사하지 않는다.
- **결정적 검사.** 같은 문서·기록이면 같은 이슈가 나온다. 저장된 기록만 검사한다.
- **규칙 변경.** 규칙을 추가·강화하면 전 곡을 다시 검사한다. 새로 BLOCK이 된 곡은 이미 활성화된 팩을 멈추지 않고, 다음 활성화(재고정·새 버전)부터 막는다. 대신 WARN 이슈로 알린다.

## 7. 자동 추출

하지 않는다(결정 D2, 2026-10-15). 조항 표시와 값 입력은 분할 화면에서 사람이 한다. 대량 카탈로그는 일괄 등록(4.D)으로 받는다. 계약서를 외부 모델로 보내는 경로가 없으므로 그에 따른 보안 검토도 필요 없다.

## 8. 무결성과 보안

- **저장.** 원문은 오브젝트 저장소에 암호화해 저장하고, DB에는 해시·메타데이터만 둔다. 읽을 때마다 해시를 다시 계산해 대조한다(봉인 저장소와 같은 방식).
- **불변.** 원문은 지우거나 덮어쓰지 않는다. 잘못 올린 문서는 `REJECTED`로 두고 기록과의 연결을 끊는다. 보관 기간이 끝난 원문의 폐기는 해시와 폐기 기록을 남기고 한다.
- **공개.** 공개본(Manifest)에는 원문도 digest도 그대로 나가지 않는다. 지금처럼 커밋먼트로 가린다.
- **열람.** 원문 다운로드에는 열람자 워터마크를 넣고 열람 기록을 남긴다.

## 9. 진행 체크리스트

진행 항목(S)과 결정 사항(D)을 체크 항목으로 관리한다.

- **진행 항목:** 끝나면 체크하고 "완료(날짜): 내용, 커밋"을 덧붙인다.
- **결정 사항:** 정해지면 체크하고 "결정(날짜, 결정한 사람): 내용"을 덧붙인다.
- **막힌 항목:** 진행 항목에는 그 항목을 막는 결정을 적어 둔다. 결정이 나기 전에는 그 항목을 시작하지 않는다(또는 결정에 기대지 않는 부분만 한다).
- **제안:** 결정 사항 아래의 "제안"은 검토용 권고안이다. 받아들이면 체크하고 결정 내용으로 옮긴다.
