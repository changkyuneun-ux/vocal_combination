# 원천 문서 관리와 권리·정책 입력·조회 설계

- 작성일: 2026-10-15 (설계 초안, 미구현)
- 관련 문서: [시스템 아키텍처 및 업무 분리안](시스템_아키텍처_및_업무분리안_20261012.md), `03_dobedupop_플랫폼설계/최신설계/데이터모델_v2.8.md`(3.3 권리 주장, 정책 폼→MDRL 텍스트), `백오피스_IA_와이어프레임_Userflow.md`(표준 계약 관리, 동의 계약서 열람)

facts IR과 정책 IR은 정산 엔진이 읽는 형식이라 권리자가 읽거나 직접 쓰기 어렵다. 이 문서는 사람이 다루는 것(계약서와 입력 화면)과 기계가 다루는 것(봉인 IR)을 나누고, 그 사이를 근거 연결로 잇는 설계를 제안한다.

## 1. 지금 상태

| 항목 | 지금 | 문제 |
| --- | --- | --- |
| 권리 사실(facts) | 운영 백오피스에서 주장·위임을 한 행씩 폼으로 입력 | 계약서 한 장에서 나오는 주장 여러 개를 따로 입력한다. 무엇을 근거로 입력했는지 남지 않는다 |
| 증빙 | 주장의 "증빙 digest", 동의의 "계약서 URI", 위임의 "출처 참조"를 문자열로 직접 입력 | 원문을 올리고 보관하는 곳이 없다. digest를 사람이 계산해 넣어야 한다 |
| 정책 | MDRL 텍스트를 편집창에 직접 작성해 컴파일 | 권리자가 쓸 수 없다. 데이터모델 v2.8의 "폼 → MDRL 텍스트 생성"은 아직 구현되지 않았다 |
| 조회 | 봉인 digest, IR JSON, MDRL 텍스트 | 일반 사용자는 "그래서 누가 얼마를 받는가"를 알 수 없다 |

엔진 쪽 바탕은 이미 있다. 권리 주장의 증빙 digest는 facts IR(`claim.evidence`)에 들어가 봉인되고, 공개본에서는 커밋먼트로 가려진다. 따라서 원문 저장소만 붙이면 봉인된 facts가 원문을 가리키게 된다.

## 2. 원칙

1. **세 층을 나눈다.**

   | 층 | 무엇 | 누가 다루나 |
   | --- | --- | --- |
   | 원천 문서 | 계약서·동의서·위임장·증빙 원문(PDF·스캔·서명본) | 사람이 올리고 읽는다 |
   | 구조화 기록 | 주장·위임·동의·정책 폼 값(행) | 사람이 입력·확인한다. 편집 단위다 |
   | 봉인 IR | facts·정책 IR(JSON, digest) | 시스템만 만든다. 사람에게는 "봉인됨" 배지와 사람이 읽는 요약으로만 보여 준다 |

2. **모든 구조화 기록은 근거를 가리킨다.** 기록마다 원천 문서와 그 안의 조항(페이지·인용)을 연결한다. 근거가 없는 기록은 `ASSERTED`로만 저장된다.
3. **플랫폼은 권리를 정하지 않는다.** 자동 추출은 후보를 제안하는 데까지만 쓴다. 기록을 확정하는 것은 권리자이고, 상대 당사자 확인 또는 플랫폼 확인(KYB·계약 대조)을 거쳐 `VERIFIED`가 된다.
4. **원문은 불변이고 내용 주소로 가리킨다.** 원문을 고치면 새 문서 버전이 된다. 이전 기록은 이전 digest를 계속 가리키므로, 이미 봉인된 정책·발행의 근거는 바뀌지 않는다. 봉인 IR에는 원문이 아니라 digest만 들어간다.

## 3. 데이터 모델 추가

```
[source_document] 1 ──< [document_clause] 1 ──< [record_evidence] >── right_claim | mandate | consent_agreement | policy_version
       │ supersedes(이전 버전)
       └── file: 오브젝트 저장소(암호화), sha256
```

**source_document** (`doc_`): 원천 문서 한 건(한 버전).

| 컬럼 | 설명 |
| --- | --- |
| `document_id`, `version`, `supersedes` | 문서와 버전 사슬. 원문을 바꾸면 새 버전 |
| `owner_tenant_id` | 올린 테넌트(RLS) |
| `kind` | `MASTER_CONTRACT`(녹음)·`PUBLISHING`(작품)·`PERFORMER_CONSENT`(실연 동의)·`MANDATE`(위임·전속)·`PLATFORM_CONTRACT`·`EVIDENCE`(기타 증빙) |
| `title`, `parties[]`, `effective_from`·`effective_to` | 사람이 붙이는 색인 정보 |
| `file_sha256`, `byte_size`, `mime`, `page_count`, `storage_uri` | 원문 파일. digest가 봉인에 들어가는 값이다 |
| `origin` | `UPLOADED`(자체 계약서) · `TEMPLATE_SIGNED`(표준 계약 마법사로 만들고 서명) · `IMPORTED`(일괄 등록) |
| `status` | `UPLOADED → IN_REVIEW → CONFIRMED`, 또는 `REJECTED` |
| `confidentiality` | 열람 범위(소유 테넌트·당사자·플랫폼). 금액 조항 마스킹 여부 |

**document_clause**: 문서 안의 근거 조항. 페이지 번호, 영역(좌표) 또는 인용문, 조항 종류(지분·위임·이용 범위·기간·분배율), 읽어 낸 값(JSON), 만든 방법(`MANUAL` | `SUGGESTED`), 상태(`PROPOSED | ACCEPTED`).

**record_evidence**: 구조화 기록과 조항의 연결(다대다). 계약서 한 장이 주장 여러 개의 근거가 되고, 주장 하나가 여러 문서(예: 계약서 + 부속 합의서)를 근거로 가질 수 있다.

**기존 컬럼의 정리.**

| 기존 | 바뀌는 점 |
| --- | --- |
| `right_claim.evidence_digest` | 직접 입력하지 않는다. 연결된 근거 문서들의 digest를 정렬해 만든 값을 시스템이 채운다. 그대로 facts IR `evidence`로 봉인된다 |
| `consent_agreement.source_contract_uri` | `source_document` 참조로 바꾼다 |
| `mandate.source_ref` | 근거 연결로 바꾼다. 위임도 증빙 digest를 봉인에 넣으려면 MDRL facts 규격의 mandate에 `evidence` 필드를 더해야 한다(엔진 규격 변경, 결정 필요) |
| `policy_version` | 정책의 근거(플랫폼 계약·권리자 합의서)를 연결한다. 정책 IR에는 넣지 않는다(정책의 근거는 승인 서명이다) |

## 4. 입력 흐름

### A. 자체 계약서가 있을 때 (업로드)

1. **문서함에 올린다.** 끌어다 놓기로 올리고, 종류·당사자·기간을 고른다. 같은 파일(같은 해시)은 다시 올라가지 않는다.
2. **조항을 표시한다.** 분할 화면 왼쪽에 원문, 오른쪽에 입력 폼이 있다. 원문에서 문장을 끌어 선택하면 조항이 되고, 폼의 필드에 연결된다. 자동 추출을 켜면 조항 후보와 값이 미리 채워지고(신뢰도 표시), 사람이 받아들이거나 고친다.
3. **기록을 만든다.** 한 문서에서 나온 기록(예: 녹음 100% 주장, 작가 2명 50%씩, 멤버 7명 → 소속사 위임)을 한 화면에서 함께 저장한다. 저장 직후 상태는 `ASSERTED`다.
4. **확인한다.** 상대 당사자(예: 작가)에게 "이 계약서의 이 조항으로 이렇게 등록됐다" 확인 요청이 간다. 상대가 확인하거나 플랫폼이 계약 대조를 마치면 `VERIFIED`가 된다. 이의가 있으면 분쟁으로 넘어간다(기존 분쟁 흐름).

```
┌─ 원천 문서: 빅히트-멤버 전속계약서 v2 (12쪽) ─────────┬─ 이 문서에서 만든 기록 ─────────────────────────┐
│  p.4  제7조(실연 수익의 수령)                            │ ① 위임  정국 → 빅히트 뮤직(소속사) · 실연 · 100%   │
│  ┌───────────────────────────────────────────────┐ │    근거: p.4 제7조 1항  ● 확인됨(정국)             │
│  │ 을은 본 계약 기간 중 발생하는 실연 관련 수익의  │ │ ② 위임  지민 → 빅히트 뮤직(소속사) · 실연 · 100%   │
│  │ 수령을 갑에게 위임한다. ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓      │─┼─▶  근거: p.4 제7조 1항  ◐ 확인 대기             │
│  └───────────────────────────────────────────────┘ │ ③ 기간  2025-01-01 ~ 2027-12-31  근거: p.2 제3조    │
│  [조항 선택] [자동 추출 후보 보기]                       │ [기록 추가]  [모두 저장(ASSERTED)]  [확인 요청]    │
└──────────────────────────────────────────────────────┴────────────────────────────────────────────────┘
```

### B. 계약서가 없을 때 (최초 작성)

자체 계약서 없이 플랫폼에서 처음 권리를 정하는 경우(예: 팬앱 전용 2차 이용 허락)는 표준 계약 템플릿으로 작성한다.

1. **질문형 마법사.** "이 곡의 녹음 권리자는?", "작품 지분은?", "멤버 실연 몫은 누가 받나(본인/소속사)?", "허락 범위는(지역·매체·기간)?"을 차례로 묻는다. 답은 처음부터 구조화 값이다.
2. **사람이 읽는 계약서 미리보기.** 답으로 표준 계약서 문안을 채워 보여 준다(법무가 관리하는 템플릿 버전).
3. **전자서명.** 당사자가 서명하면 서명본 PDF가 원천 문서(`TEMPLATE_SIGNED`)가 되고, 마법사 답이 그대로 주장·위임·동의 기록이 된다. 조항과 값이 템플릿에서 이미 대응되므로 추출이 필요 없고, 모든 당사자가 서명했으므로 바로 `VERIFIED`다.

실연자 앱의 동의 서명도 같은 방식이다. 지금은 범위 값만 저장하지만, 서명 시 동의서 문안(PDF)을 원천 문서로 남기면 IA의 "체결된 동의 계약서 원문 열람"이 된다.

### C. 분배 규칙(정책)

권리자는 MDRL을 쓰지 않는다. 폼으로 작성하고, 시스템이 MDRL 텍스트를 만들어 컴파일한다(데이터모델 v2.8의 폼 → `policy_version.source_text` 흐름).

```
┌─ 분배 규칙: Dynamite 팬앱 전용 (v2 초안) ───────────────────────────────────────────────┐
│ 1차 분할   플랫폼 [25]%   운영 [5]%   권리자 [70]%          (플랫폼 계약 허용 구간: 권리자 65~75%) │
│ 2차 분할   녹음 [40]%   실연 [45]%   작품 [15]%                                            │
│ 실연 몫    ◉ 참여 멤버 고정 40% + 부른 시간 60%   ○ 부른 시간만   1인 상한 [50]%            │
│            ☑ 위임이 있으면 위임받은 쪽이 받는다                                            │
│ ── 이렇게 나뉩니다(구매 3,300원 1건, 원곡 배치 조합) ───────────────────────────────────── │
│ 플랫폼 825 · 운영 165 · 빅히트(레이블) 924 · 빅히트(소속사) 1,040 · 작가 2명 173씩          │
│ ── 쉬운 말로 ───────────────────────────────────────────────────────────────────────────── │
│ "매출의 70%가 권리자 몫이고, 그중 40%는 녹음 권리자에게, 45%는 그 조합을 부른 멤버에게…"  │
│ [MDRL 텍스트 보기(고급)]  [이전 버전과 비교]  [저장 → 컴파일 → 승인 요청]                  │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

- **예시 계산은 엔진이 한다.** 화면에서 따로 계산하지 않는다. 현재 facts와 대표 조합으로 엔진 시뮬레이션을 돌린 결과다(봉인하지 않음). Dynamite 예시의 "구매 1건 계산" 표와 같은 방식이다.
- **허용 구간을 미리 막는다.** 플랫폼 계약·계승 규칙(하한·상한)을 넘는 값은 입력 단계에서 막는다. 컴파일 진단은 마지막 방어선이다.
- **고급 모드.** MDRL 텍스트를 직접 고치는 화면은 운영·고급 사용자에게만 열어 둔다. 직접 고친 정책은 폼으로 되돌릴 수 없다는 표시를 한다.

### D. 일괄 등록

카탈로그가 큰 권리자는 크레딧 시트(CSV·스프레드시트)를 올린다. 행마다 원천 문서를 지정하고, 연동 허브처럼 줄별 결과(적용·거부 사유)를 보여 준다.

## 5. 조회: 사람이 읽는 보기

봉인 IR을 그대로 보여 주지 않는다. 같은 행에서 사람이 읽는 보기를 만들고, 봉인과 일치하는지만 배지로 알린다.

| 보기 | 내용 |
| --- | --- |
| **권리 요약** | 문장으로 보여 준다. 예: "녹음: 빅히트 뮤직(레이블) 100%", "작품: David Stewart 50%, Jessica Agombar 50%", "실연: 멤버 7명, 실연 몫은 빅히트 뮤직(소속사)이 받음(위임)". 문장마다 근거 문서·쪽으로 가는 링크가 있다 |
| **권리 지도** | 곡 → 녹음·작품 → 스템·보이스 → 권리자 → 위임받은 쪽을 그래프로 보여 준다. 분쟁 중인 연결은 표시한다 |
| **정책 설명** | 쉬운 말 설명과 예시 계산표, 이전 버전과 바뀐 점("실연 1인 상한 60% → 50%") |
| **봉인 상태 배지** | "봉인됨 2026-02-01 · 서명 3/3(편집·승인·활성화) · 원문 일치 ✓". digest와 JSON은 "개발자 보기"에 접어 둔다 |
| **근거 추적** | 정산 라인 → 발행 봉인 → 권리 주장 → 근거 조항 → 원문 쪽. ⑧ "한 건 추적"을 원문까지 늘린 것이다 |

역할에 따라 보이는 범위가 다르다.

| 누구 | 보이는 것 |
| --- | --- |
| 권리자(소유 테넌트) | 자기가 올린 문서 전체, 자기 곡의 요약·지도·정책 |
| 상대 당사자 | 자기와 관련된 조항과 기록(예: 작가는 작품 지분 조항). 다른 당사자의 금액 조항은 가린다 |
| 실연자 앱 | 내 동의서 원문, 나를 가리키는 주장과 그 근거 조항(이의제기 화면에서 함께 보인다) |
| 플랫폼 운영 | 전부 보되 원문 열람은 열람 기록에 남고(조회 통제 1단계), 금액 조항은 기본 마스킹(2단계) |

## 6. 자동 추출(선택)

- **방식.** OCR과 언어 모델로 조항 후보와 값(당사자·지분·기간·범위)을 제안하고 신뢰도를 보여 준다.
- **한계.** 추출 결과는 봉인 입력이 아니다. 사람이 받아들인 기록만 저장되고, 받아들인 사람과 시각이 남는다.
- **위험.** 계약서는 영업 비밀과 개인정보를 담는다. 외부 모델로 보낼지, 내부 모델만 쓸지, 권리자가 켜고 끄게 할지 정해야 한다. 정하기 전에는 수동 조항 표시만으로 운영한다.

## 7. 무결성과 보안

- **저장.** 원문은 오브젝트 저장소에 암호화해 저장하고, DB에는 해시·메타데이터만 둔다. 읽을 때마다 해시를 다시 계산해 대조한다(봉인 저장소와 같은 방식).
- **불변.** 원문은 지우거나 덮어쓰지 않는다. 잘못 올린 문서는 `REJECTED`로 두고 기록과의 연결을 끊는다. 보관 기간이 끝난 원문의 폐기는 해시와 폐기 기록을 남기고 한다.
- **공개.** 공개본(Manifest)에는 원문도 digest도 그대로 나가지 않는다. 지금처럼 커밋먼트로 가린다.
- **열람.** 원문 다운로드에는 열람자 워터마크를 넣고 열람 기록을 남긴다.

## 8. 단계별 구현 제안

| 단계 | 범위 | 효과 |
| --- | --- | --- |
| 1 | `source_document` 저장소·업로드·열람, 기존 증빙·계약서 문자열 필드를 문서 선택기로 교체, 권리 요약 보기 | 원문이 한곳에 남고, 봉인된 facts가 실제 원문을 가리킨다 |
| 2 | 정책 폼 편집기 + 엔진 예시 계산 + 쉬운 말 설명 + 버전 비교 | 권리자가 MDRL 없이 분배 규칙을 만든다 |
| 3 | 분할 화면 근거 연결(조항), 상대 당사자 확인 → `VERIFIED` | 기록마다 근거가 붙고 확인 절차가 생긴다 |
| 4 | 표준 계약 템플릿 마법사 + 전자서명, 실연 동의서 원문 | 계약서가 없는 권리자도 처음부터 근거를 갖고 시작한다 |
| 5 (선택) | 자동 추출 | 대량 카탈로그 입력 시간을 줄인다 |

## 9. 결정이 필요한 것

1. **전자서명 공급자.** 국내 공급자를 쓸지, 자체 서명(플랫폼 서명키)으로 갈지 정해야 한다.
2. **자동 추출.** 도입할지, 외부 모델을 써도 되는지 정해야 한다.
3. **원문 보관.** 보관 위치·기간·폐기 규칙(계약 종료 후 몇 년)을 정해야 한다.
4. **위임 증빙의 봉인.** MDRL facts의 mandate에 `evidence`를 더할지 정해야 한다(엔진 규격 변경, 적합성 기대값 갱신).
5. **확인 절차.** 상대 당사자 확인을 필수로 할지(모든 주장), 일부만 할지(지분·위임만) 정해야 한다.
6. **표준 계약 템플릿.** 법무가 관리하는 템플릿의 종류와 버전 관리 방식을 정해야 한다.
