# MVP 결정과 정책 고려사항

- 작성일: 2026-10-19
- 용도: MVP·Dynamite 데모를 설명할 때 "왜 이렇게 동작하는가"를 답하는 문서다. 설계 문서들에 흩어진 결정과, 구현하면서 새로 정한 정책을 한곳에 모았다.
- 근거 문서: [MVP 진행계획](MVP_진행계획_Dynamite데모_20261016.md)(MD), [원천 문서 설계](원천문서_관리와_권리·정책_입력·조회_설계_20261015.md)(D), [테넌트 관리 기준과 정책](테넌트_관리_기준과_정책_20261019.md)(TD·TN), [아키텍처](시스템_아키텍처_및_업무분리안_20261012.md), [데모 가이드](../06_MVP/dobedupop/docs/데모_가이드.md)
- 상태 표기: **확정** = 사용자가 정했다. **우선 진행** = 제안대로 구현했고 법무 등 확인 뒤 바뀔 수 있다. **MVP 한정** = 데모를 위해 단순화했고 상용 전에 바꾼다. **미결** = 아직 정하지 않았다.

## 1. 시연 전에 먼저 말할 것

1. **가상 사례다.** 곡 크레딧·멤버·가창 시간만 실제이고, 지분·계약·가격(3,300원)·판매량은 가정이다. 실명은 내부 시연에만 쓴다(MD5).
2. **플랫폼은 권리를 결정하지 않는다.** 운영은 검증·집행만 한다. 정책 편집·승인·활성화는 권리자가 하고, 플랫폼이 대신하려면 권리자가 맡긴 업무만 대행하며 기록이 남는다(TD3, 위임 대행).
3. **권리를 등록하려면 권리 테넌트가 있어야 한다.** 신탁단체·유통 파트너는 권리를 만들지 않는 참여 기관이고, 실연자·팬은 테넌트 없이 개인 계정으로 일한다(TD1).
4. **돈은 당사자에게 간다.** 테넌트도 계정도 돈을 받지 않는다. 그래서 빅히트는 Dynamite를 등록했어도 작가 몫 정산은 볼 수 없다(테넌트 정책 3절).
5. **누가 무엇을 보는지는 네 열쇠로 정한다.** 소유(등록한 쪽)·당사자(그 몫의 주인)·본인·연결(참여 기관). 데이터베이스가 행 단위로 강제한다.
6. **돈의 흐름을 바꾸는 기록은 상대가 확인해야 확정된다.** 지분·위임·연결은 한쪽 입력만으로 성립하지 않는다(D5, TD10).
7. **한 사람이 정책을 편집·승인·활성화까지 하지 못한다.** 예외는 혼자인 독립 아티스트가 법무 승인 표준 템플릿을 그대로 쓸 때뿐이다(TD13).
8. **숫자는 1원까지 맞는다.** 정산은 실행 뒤 다른 프로세스가 다시 계산해 맞춰 보고, 확정은 다른 사람이 한다.

## 2. 결정 사항

### 2.1 조직·계정·데이터 범위(테넌트 정책)

| ID | 결정 | 왜 | 데모에서 보이는 모습 | 상태 |
| --- | --- | --- | --- | --- |
| TD1 | 참여 구분: 권리 테넌트·참여 기관·개인·플랫폼 운영. 화면의 "테넌트"는 권리 테넌트만 | "테넌트 = 권리자"라는 혼동을 없앤다 | 운영 → 9 온보딩에 권리 테넌트·참여 기관·개인 계정이 따로 있다 | 확정 |
| TD2 | 한 테넌트에 여러 당사자는 같은 법인의 여러 권리 역할, 또는 계열사 관리 위임 계약이 있을 때만. 계좌 예금주는 당사자와 같아야 한다 | 남의 돈을 한 조직이 모아 받지 못하게 | 빅히트 = 레이블·소속사 당사자 둘(같은 사업자번호) | 확정 |
| TD3 | 운영 계정에 권리 결정 역할(정책 편집·승인·활성화·발행)을 주지 않는다. 당사자 등록은 "온보딩" 역할 | 플랫폼 = 검증자·집행자 | 운영 인력 화면에서 권리 역할을 고를 수 없다 | 확정 |
| TD4 | 운영은 조직의 첫 관리자만 발급, 담당자는 조직 관리자가 관리 | 고객 조직의 인사를 운영이 떠안지 않는다 | 빅히트 관리자가 포털 "담당자 계정"에서 4명을 초대 | 확정 |
| TD5 | 확인(KYB): 확인됨 = 사업자·대표자·플랫폼 계약, 활성 = 권리 보유 증빙(참여 기관은 신탁 허가·유통 계약). MVP는 체크리스트 | 확인 없이 권리를 팔지 않는다 | 조직 상세의 확인 항목 체크와 상태 버튼 | 확정(진위 확인 연동은 상용) |
| TD6 | 플랫폼 위탁 당사자(예: 해외 작가)의 명세는 운영이 문서로 보내고, 관리를 넘기면 넘겨받은 쪽이 과거 명세도 본다 | 플랫폼 밖 당사자도 돈을 받는다 | 작가 2명은 플랫폼 위탁, 운영이 원문 대조로 확인 | 확정 |
| TD7 | 정지 = 판매 중지·지급 보류(정산은 계속 계산), 해지 = 미정산분까지 마감 후 종료 | 정지 중에도 금액 근거는 계속 남긴다 | 상태 설명 문구, 지급 보류 사유 `TENANT_SUSPENDED` | 확정 |
| TD8 | 공용 명부에는 권리자로 활동하는 당사자만. 팬·개인 실연자는 관리 주체와 그 사람이 나오는 곡의 테넌트만 본다 | 개인 정보 최소 노출 | 다른 레이블은 멤버 당사자를 목록에서 못 본다(정확한 id로는 찾는다) | 확정 |
| TD9 | 계정 하나에 소속 여러 개, 로그인 뒤 일할 소속을 고른다 | 사람 하나에 로그인 하나 | 머리글 "소속" 선택(소속이 둘 이상일 때) | 확정 |
| TD10 | 연결(신탁·유통)은 양쪽 확인으로만 성립, 끊으면 그 뒤 발행·정산부터 | 돈의 흐름을 일방으로 바꾸지 못하게 | 가상 신탁단체의 `lnk_trust_demo`가 확인 대기 | 확정 |
| TD11 | 신탁 연결이 확인되면 작가 → 신탁단체 작품 몫 위임을 자동 기록 | 신탁 범위의 작품 몫은 신탁단체가 받는다 | 확인하면 위임이 생기고 경고가 뜬다(3절 MP3) | 우선 진행(신탁 범위·상호관리 법무 확인) |
| TD12 | 신탁단체·유통 파트너는 참여 기관 화면(`partner.`)을 쓰고 권리자 포털에는 못 들어온다 | 권리를 만들지 않는 조직에 등록 권한을 주지 않는다 | 신탁단체 관리자로 포털 로그인 시 거부 | 확정 |
| TD13 | 1인 테넌트는 법무 승인 표준 템플릿을 값 그대로 쓴 정책만 혼자 승인·활성화 | 혼자서는 직무 분리를 지킬 수 없고, 플랫폼이 승인하면 TD3과 어긋난다. 템플릿 승인이 두 번째 눈이다 | 정책 화면 "표준 템플릿으로 만들기", 감사 `SOD_TEMPLATE_EXEMPTION` | 확정 |

### 2.2 권리 기록과 원천 문서

| ID | 결정 | 왜 | 데모에서 보이는 모습 | 상태 |
| --- | --- | --- | --- | --- |
| D1 | 전자서명은 국내 사업자(미정). 그때까지 개발용 공급자 | 공급자만 바꾸면 되게 인터페이스로 분리 | 작가는 "공급자 서명" 통지로 서명 | 우선 진행(사업자 미정) |
| D2 | 계약서 자동 추출은 하지 않는다 | 원문을 외부 모델에 보내지 않는다 | 조항 표시는 사람이 한다 | 확정 |
| D3 | 원문은 국내 리전·암호화·삭제 잠금, 효력 종료 후 10년 보관 | 영업 중요서류 보관 기간 | 원천 문서 화면, 폐기 기록 | 우선 진행(기간 법무 확인) |
| D4 | 위임에도 근거 문서를 봉인한다 | 위임은 돈이 가는 곳을 바꾼다 | 위임 근거 없으면 경고 | 우선 진행 |
| D5 | 지분·위임·권리자 지정은 상대 확인을 받아야 확정(VERIFIED) | 한쪽 주장만으로 돈이 움직이지 않게 | 멤버가 실연자 앱에서 56건 확인, 작가는 기한 뒤 원문 대조 | 우선 진행 |
| D6 | 표준 계약 5종, 법무 작성 ≠ 승인 | 계약 문안의 직무 분리 | 표준 계약 화면 | 우선 진행 |
| D7 | 곡 유형별 필수 근거 문서, 없으면 차단(BLOCK) | 근거 없는 지분으로 판매하지 않는다 | 정합성 점검 | 우선 진행 |
| D8 | 차단 = 금액·귀속을 틀리게 만드는 것, 경고 = 운영 위험. 경고 기한 14일, 위험 수용은 운영 요청 ≠ 컴플라이언스 승인 | 정산은 맞지만 위험한 것을 구분 | 정합성 점검의 위험 수용 | 우선 진행 |

### 2.3 MVP 범위·배포

| ID | 결정 | 데모에서 보이는 모습 | 상태 |
| --- | --- | --- | --- |
| MD1·MD2 | MVP는 `06_MVP/dobedupop`, 기존 구현은 이력째 이동 | — | 확정 |
| MD3 | 코어가 세션 발급. 운영 = 비밀번호 + 인증 앱 코드 + IP 제한, 포털·참여 기관 = 비밀번호(+선택), 실연자 = 본인 인증 코드 | 로그인 화면, 데모만 페르소나 빠른 로그인 | 확정 |
| MD4 | 서브도메인 = 앱 = 채널: `portal`·`partner`·`artist`·`ops`·`demo` | 주소마다 그 채널만 통과 | 확정(`partner`는 TD12로 추가) |
| MD5 | 실명은 내부 시연만, 외부용 가명 세트는 별도 | 화면의 가상 사례 표시 | 확정(가명 세트는 미작성) |
| MD6 | 데모 서버 한 대에 Docker Compose | — | 확정 |
| MD7 | 데모 진행판은 별도 앱(데모 환경에만) | `demo.` 주소 | 확정 |
| MD8 | 72시간 발행 승인 큐는 넣지 않는다. 게이트 통과 즉시 봉인 | 팬 조합이 바로 발행 | 확정(상용 단계 작업) |

## 3. 구현하면서 정한 정책(MVP 정책)

설계 문서에 없었거나 구체적이지 않아 구현 중에 정한 것이다. 시연 때 질문이 나오기 쉬운 순서로 적었다.

| ID | 정책 | 이유·설명 | 상태 |
| --- | --- | --- | --- |
| MP1 | 정책은 화면의 "표준 템플릿으로 만들기"(API `from-template`)로 만들어야 템플릿 정책으로 인정한다. 같은 문장을 손으로 써서 컴파일하면 일반 정책(직무 분리 적용) | 템플릿 출처를 기록으로 남겨야 예외를 검증할 수 있다 | 확정(TD13 구현) |
| MP2 | 정책은 컴파일할 때의 권리 사실에 고정된다. 나중에 생긴 위임(예: 신탁)은 정책을 재고정하거나 다시 승인해야 반영된다 | 판매 시점의 근거를 바꾸지 않는다(봉인) | 확정(설계 그대로) |
| MP3 | 신탁 위임이 생겨도 정책의 작품 몫이 "위임받은 곳이 받는다"가 아니면 신탁단체가 받지 못한다. 이때 경고 `TRUST_NOT_ROUTED`를 띄운다 | 분배 방식은 권리자가 정한다. 플랫폼은 알려 줄 뿐 바꾸지 않는다 | 확정 |
| MP4 | 신탁 범위(이용 매체)는 아직 구분하지 않는다. 신탁 위임은 그 곡의 모든 이용에 적용된다 | 위임 기록에 이용 범위가 없다 | MVP 한정(TN13) |
| MP5 | 확인됨 상태 조직은 권리를 등록할 수 있지만 팩·정책 활성화와 판매는 못 한다. 데모의 빅히트는 녹음 계약서 원문을 확인한 뒤 활성이 된다 | 등록은 준비 작업, 판매는 확인 뒤 | 확정(TD5·TD7 구현) |
| MP6 | 실연 몫 전부(100%)를 확정된 위임으로 소속사에 넘긴 멤버는 지급 정보가 없어도 경고하지 않는다 | 그 멤버는 직접 돈을 받지 않는다 | 확정 |
| MP7 | 플랫폼 밖 작가(위탁 당사자)의 작품 이용허락은 플랫폼 온보딩이 맺고, 작가 지분 확인은 14일 기한 뒤 운영이 원문 대조로 확정한다 | 빅히트는 다른 조직의 당사자를 대신 확정할 수 없다 | 확정 |
| MP8 | 독립 아티스트 1인 온보딩은 본인 인증을 마친 개인 계정만. 그 사람의 당사자 관리가 1인 테넌트로 옮겨 가고, 실연자 앱은 그대로 쓴다 | 본인 확인이 사업자 확인을 대신한다 | 확정 |
| MP9 | 위임 대행 업무는 "권리 데이터·원천 문서 등록"만 맡길 수 있다. 대행 중에는 그 테넌트 데이터만 보이고 요청마다 기록이 남는다 | 정책 결정은 위임할 수 없다(TD3) | 확정 |
| MP10 | 공용 명부에서 개인을 숨겨도 정확한 당사자 id로는 찾을 수 있다 | 곡을 등록하려면 멤버를 지정해야 한다 | 확정 |
| MP11 | 조직 관리자는 자기 역할을 바꾸거나 자기 계정을 잠그지 못한다. 다른 조직에도 소속된 사람의 계정은 기본 소속 조직의 관리자만 잠근다 | 잠금은 그 사람 전체에 영향 | 확정 |
| MP12 | 로그인 5회 실패 시 15분 잠금, 상태를 바꾸는 요청은 CSRF 헤더 필요, 세션은 그 서브도메인에서만 | 기본 보안 | 확정 |
| MP13 | 지급: 최소 지급액 10,000원 미만은 이월, 첫 지급 전 30일 보류, 계좌 변경 후 72시간 보류, 계좌를 바꾼 사람은 그 지급을 실행하지 못한다. 해외 당사자는 원천징수 | 지급 사고 방지 | 우선 진행(세무 확인) |
| MP14 | 이상거래 의심 매출은 보류되어 정산에서 빠지고, 해제하면 다음 정산에 들어간다 | 사기 대응 | 확정 |
| MP15 | 운영이 연동 허브에서 직접 등록하는 상품 대응은 확인 절차 없이 확정으로 들어간다(운영 대행으로 남김) | 파트너 제안 → 권리 테넌트 확인 경로와 별개 | MVP 한정(TN15) |
| MP16 | 분개 머리(`journal_entry`)·지급 실행(`payout_run`) 표에는 행 단위 보안이 없다(금액은 보안이 있는 표에 있다) | 조회 API가 범위를 정한다 | MVP 한정(TN16) |
| MP17 | 기존 개발·시험 계정 일부(`usr_editor` 등)는 시험을 고정하려고 플랫폼 권리 역할을 그대로 갖는다. 새로 발급할 수는 없다 | 시험 데이터 호환 | MVP 한정 |
| MP18 | 데모는 가상 시계(1/1 온보딩 → 5/1 지급), 가상 PSP(지급 1분 뒤 완료), 개발용 본인 인증·전자서명 공급자를 쓴다 | 시연 시간을 줄인다 | MVP 한정 |

## 4. 시연 때 자주 나올 질문

| 질문 | 답 | 근거 |
| --- | --- | --- |
| 플랫폼 운영자가 정책을 고칠 수 있나? | 없다. 운영 계정에는 정책 역할이 없다. 권리자가 맡긴 등록 업무만 대행할 수 있고, 대행 기록은 그 권리자가 본다 | TD3, MP9 |
| 빅히트가 Dynamite를 등록했는데 왜 작가 몫을 못 보나? | 곡 데이터는 등록한 쪽이 보지만, 돈 데이터는 그 몫의 주인만 본다 | 테넌트 정책 3절 |
| 신탁단체는 왜 포털에 못 들어오나? | 권리를 만들지 않기 때문이다. 연결로 위임받은 일에 필요한 것만 본다 | TD12 |
| 신탁 연결을 확인했는데 왜 신탁단체가 돈을 안 받나? | 이 데모 정책의 작품 몫이 위임대로 가게 되어 있지 않다. 권리자가 정책을 고쳐 다시 승인해야 한다. 경고가 이를 알린다 | MP2, MP3 |
| 혼자 활동하는 아티스트는 어떻게 하나? | 본인 인증 뒤 1인 테넌트를 만들고, 표준 템플릿을 그대로 쓰면 혼자 정책을 활성화한다 | TD13, MP8 |
| 레이블 승인 없이 팬 조합이 바로 나오나? | MVP는 게이트(동의·근거·정합성)를 통과하면 바로 봉인한다. 72시간 승인 큐는 상용 단계다 | MD8 |
| 조직이 문제를 일으키면? | 컴플라이언스가 정지한다. 판매가 멈추고 지급이 보류되며, 정산 계산은 계속된다 | TD7 |
| 숫자가 맞는지 어떻게 아나? | 정산 실행 뒤 별도 검증 프로세스가 다시 계산해 맞춰 보고, 다른 담당이 확정한다. 지급 결과는 예시 보고서와 같다 | 아키텍처 직무 분리 |

## 5. 상용 전에 확인·결정할 것

- [ ] **C1** 신탁 범위·상호관리(해외 작가) 구조와 신탁단체 수령 방식 법무 확인 (TD11, MP4·TN13)
- [ ] **C2** 원문 보관 기간 10년 법무 확인 (D3)
- [ ] **C3** 지급 정책 값(원천징수율·보류 기간·최소 지급액) 세무 확인 (MP13)
- [ ] **C4** 전자서명 사업자 선정, 실연자 동의서를 자체 서명으로 둘지 (D1)
- [ ] **C5** 외부 시연용 가명 데이터 세트, 실명 사용 법무 확인 (MD5)
- [ ] **C6** 사업자 진위 확인 연동, 본인 인증 공급자, 운영 SSO 실제 연결 (TD5, MD3)
- [ ] **C7** 운영 직접 상품 대응을 위임 대행으로 묶을지 (MP15·TN15)
- [ ] **C8** RLS 없는 표를 플랫폼 전용으로 바꿀지 (MP16·TN16)
- [ ] **C9** 72시간 발행 승인 큐 (MD8, 아키텍처 다음 작업 18)
- [ ] **C10** 표준 분배 규칙 템플릿 목록과 문안(지금은 법무 초안 2종 시드)을 법무가 확정 (TD13)

## 6. 이 문서를 고치는 법

- 새 결정이 생기면 원래 문서(MVP 진행계획·원천 문서 설계·테넌트 정책)에 체크 항목으로 먼저 적고, 여기 2절 표에 한 줄로 옮긴다.
- 설계 문서에 없이 구현하면서 정한 동작은 3절에 `MP` 번호로 더한다. 상용 전에 바꿔야 하면 상태를 "MVP 한정"으로 두고 5절에 확인 항목을 단다.
