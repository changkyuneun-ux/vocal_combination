# 예시: Dynamite 보컬 조합 2차 이용, 권리 생성에서 지급까지

- 작성일: 2026-10-12
- 원본(공유 문서의 "예시: Dynamite 2차 이용" 탭): https://claude.ai/code/artifact/9db7d516-16a3-4822-a995-ea0671a5fba3
- 상위 문서: [시스템 아키텍처 및 업무 분리안](시스템_아키텍처_및_업무분리안_20261012.md)

곡 Dynamite를 보컬리스트 4명이 녹음한 스템으로 팬이 조합하는 팬앱 전용 2차 이용을, 실제 MDRL 엔진과 정산 코어로 끝까지 돌린 결과다. 3개 조합의 구매 540건(1,782,000원)에서 환불 1건을 뺀 순매출 1,778,700원이 권리 생성 때 정한 분배율대로 나뉘고, 권리자 8명에게 1,242,780원이 지급됐다.

> 가상 예시다. 곡 제목만 빌렸고, 참여자·분배율·구간·가격은 모두 설명을 위한 가정이며 실제 권리관계·계약과 무관하다. 금액은 손으로 계산한 값이 아니라 `04_구현_소스코드/rights-core/src/scenario/dynamite.ts`를 실행해 얻은 값이다([실행 결과 JSON](예시_Dynamite/dynamite-report.json)).

## 등장 주체와 자산

권리자 5곳, 보컬리스트 4명, 팬 3명이 나온다. 팬은 권리를 갖지 않고 허락된 범위의 이용권만 갖는다.

| 주체 | 역할 | 권리·지분(가정) | 쓰는 앱 |
| --- | --- | --- | --- |
| 레이블 L | 녹음(마스터) 보유, 곡·스템 등록 | 녹음 100% | 권리자 포털 |
| 작가 W1 | 작사·작곡 | 작품 50%, 신탁단체 C에 위임 | (C가 대신 수령) |
| 작가 W2 | 작사·작곡 | 작품 50% | 권리자 포털 |
| 신탁단체 C | W1의 작품 권리 관리 | W1 몫 100% 수령 | 권리자 포털 |
| 보컬리스트 A·B·C·D | 슬롯별 보컬 스템 녹음(실연) | 자기 스템 실연 100% | 실연자 앱 |
| 소속사 G | 보컬리스트 D의 소속사 | D의 실연 권리 위임, 계약 몫 | 권리자 포털 |
| 팬 F1·F2·F3 | 조합·구매·감상 | 없음(이용권만) | 팬 앱 |
| 플랫폼 | 검증·관제·정산 집행 | 수수료·운영비 | 운영 백오피스 |

곡은 보컬을 바꿀 수 있는 슬롯 4개와 반주(MR)로 나뉘고, 보컬리스트 4명이 슬롯마다 녹음해 보컬 스템은 16개다.

| 슬롯 | 구간 | 길이 | 녹음한 보컬리스트 |
| --- | --- | --- | --- |
| 1절 | 0~40초 | 40초 | A·B·C·D |
| 프리코러스 | 40~60초 | 20초 | A·B·C·D |
| 후렴 | 60~100초 | 40초 | A·B·C·D |
| 브리지 | 100~140초 | 40초 | A·B·C·D |
| 반주(MR) | 0~199초 | 199초 | — (이 예시에서는 정산 대상 아님) |

## 전 과정 흐름

![Dynamite 예시 · 앱별 레인으로 본 11단계](images/Dynamite_전과정_흐름.png)

권리는 권리자 포털과 실연자 앱(보컬리스트)에서 정해지고, 금액은 권리 및 정산 코어에서만 계산된다. 운영 백오피스는 전 구간을 관제하고 정산 확정만 집행한다.

## 봉인되는 IR 한눈에

이 예시에서 봉인되는 IR은 다섯 종류다. 발행 봉인(S3)은 IR이 아니라, facts·정책·투영·멤버 IR 네 개의 digest를 묶어 고정하는 불변 레코드(`issue_seal`)다.

| 봉인 | IR 종류 | 형식 | 만드는 때 | 담는 내용 | 이 예시의 개수 |
| --- | --- | --- | --- | --- | --- |
| S1 | facts IR | facts 문서 | 정책 컴파일(1~2단계) | 주체·작품·녹음·보이스·스템, 권리 주장·위임(계산식 없음) | 곡당 1개(`8455359c…`) |
| S2 | 정책 IR(allocation) | 정책 문서 | 정책 컴파일(2~3단계) | 1·2차 분배율, 벡터 식, 반올림, 참조하는 facts digest | 정책 버전당 1개(`c6ef08e3…`) |
| S3-a | 투영 IR(projection) | `mdrl-projection/1` | 조합 발행(6단계) | 발행 시각 기준 역할별 기여 벡터와 권리 경로(쓰인 스템의 사용 시간 반영) | 조합당 1개 |
| S3-b | 멤버 IR(members) | `{members: 비율}` | 조합 발행(6단계) | 보컬리스트별 멤버 비율(유리수, 합 1) | 조합당 1개 |
| S4 | 매출 IR(events) + 정산 결과 IR(allocation_result) | `mdrl-allocation-result/1` | 정산 run(8~9단계) | 입력 매출, 풀·라인·보류, result_digest | run당 1쌍(3개) |
| S4-r | 역분개 결과 IR(reversal_result) | `mdrl-reversal-result/1` | 확정 후 환불 | 원 라인을 되돌리는 음수 라인 | 환불당 1개(1개) |

S3에서 facts IR과 정책 IR은 새로 만들지 않고 이미 봉인된 S1·S2를 가리키며, 투영·멤버 IR만 발행 순간 새로 만들어 봉인한다. 공개용 IR(public_facts, manifest)은 이 예시에서 만들지 않았다.

## 1~3단계: 권리 생성, 분배 규칙, 권리자 승인

권리자가 권리자 포털에서 권리 사실과 분배 규칙을 등록하고, 서로 다른 세 사람이 작성·승인·활성화해야 팩이 열린다.

**1. 권리 생성(권리자 포털).** 레이블 L이 곡·녹음·슬롯 5개·스템 17개를 등록하고, 권리 주장(녹음 100% L, 작품 W1·W2 각 50%, 스템별 실연자)과 위임(W1 → C 작품, D → G 실연)을 기록한다. 정책을 컴파일할 때 코어가 이 행들을 facts IR(S1)로 만들어 봉인한다(`mdrl:sha256:8455359c…`).

**2. 분배 규칙(MDRL 정책).** 권리 생성 때 정하는 분배율이다. 이후 모든 매출은 이 규칙으로만 나뉜다.

```text
allocation "pol_dynamite_fan" version 1 {
  uses facts "fsc_dynamite"@1 digest "mdrl:sha256:…";   // 컴파일 때 봉인된 facts digest로 고정
  scope { pack: pak_dynamite_fan; events: [PRIMARY, TRAFFIC]; currency: KRW; }
  bind { time: ISSUE_TIME; }
  tier1 {
    platform = 25%;
    ops = 5%;
    rights = 70%;
  }
  tier2 rights {
    split {
      master = graph(MASTER_OWNER) : 40%;
      performer = performance_pool(HYBRID, fixed: 40%, usage: 60%, featured_weight: 70%) |> cap(50%) : 40%;
      work = graph(WORK_AUTHOR) via mandate : 15%;
      agency = contract(pty_agency) : 5% as AGENCY;
    }
  }
  rounding { method: HIERARCHICAL_LRM_V1; tie: party_id_asc; }
}
```

- **1차 분할**: 매출을 플랫폼 25%, 운영 5%, 권리자 풀 70%로 나눈다.
- **2차 분할(권리자 풀)**: 마스터 40%는 녹음 보유자에게, 실연 40%는 조합에 들어간 보컬리스트에게, 작품 15%는 작가 지분대로(위임이 있으면 수임자에게), 소속사 5%는 계약대로 G에게 간다.
- **실연 몫(HYBRID)**: 40%는 멤버 비율(맡은 슬롯 수)대로, 60%는 실제 사용 구간 길이대로 나누고, 한 사람은 50%를 넘지 못한다.
- **반올림**: 1원 단위 최대잉여법(HIERARCHICAL_LRM_V1). 어느 단계에서도 합계가 정확히 보존된다.

**3. 승인·활성화(직무 분리).**

| 작업 | 수행자(역할) | 결과 |
| --- | --- | --- |
| 정책 컴파일 | 편집자(EDITOR) | 정책 IR(S2) 봉인 `mdrl:sha256:c6ef08e3…` |
| 정책 승인 | 승인자(WORK_APPROVER) | 승인 서명 |
| 정책 활성화 | 활성화 담당자(ACTIVATOR) | 정책 ACTIVE |
| 팩 활성화 | 활성화 담당자(ACTIVATOR) | 팩 `DYNAMITE-FAN`(팬앱 전용) ACTIVE |

팩 활성화 때 코어는 팩에 선언된 권리자 9곳이 facts의 권리 주장과 일치하는지 검사한다. 한 사람이 두 역할을 겸하면 코어가 거부한다.

## 4~6단계: 보컬리스트 동의, 이용허락 판정, 발행 봉인

보컬리스트가 실연자 앱에서 팬앱 전용 범위로 동의하면, 팬의 요청은 그 범위 안에서만 허락되고 발행 시점의 입력이 모두 봉인된다.

**4. 보컬리스트 동의(실연자 앱).** 보컬리스트 A~D가 자기 보이스 사용을 아래 범위로 허락한다. 레이블 L(녹음)과 신탁단체 C(작품)도 같은 범위로 허락한다.

| 차원 | 허락 범위 |
| --- | --- |
| 행위 | 미리듣기, 조합, 개인 소장, 앱 내 링크 공유 |
| 지역 | 한국 |
| 매체 | 팬 앱 |
| 청중 | 팬 커뮤니티 |
| 기간 | 2026-01-01 ~ 2027-01-01 |

**5. 이용허락 판정(팬 앱).** 조합에 들어간 녹음·작품·보컬리스트의 허락을 모두 만족해야 허락되고, 하나라도 범위를 벗어나거나 철회되면 거부한다(불확실하면 거부). 엔진 판정 결과다.

| 요청 | 판정 | 사유 |
| --- | --- | --- |
| 팬앱에서 vc_dyn_001 조합·감상 | PERMIT | — |
| 같은 조합을 내려받아 외부 SNS에 게시 | DENY | `GRANT_SCOPE_WIDENING` — 허락 범위 밖(다운로드·외부 매체·공개 청중) |
| 보컬리스트 D가 동의를 철회한 뒤 같은 조합·감상 | DENY | `GRANT_REVOKED` — D의 동의 철회 |

**6. 발행 봉인 S3(팬 앱 → 권리 및 정산 코어).** 발행 봉인은 IR 하나가 아니라, 조합 하나에 대해 네 IR의 digest를 묶어 고정하는 불변 레코드(`issue_seal`)다. facts IR(S1)과 정책 IR(S2)은 이미 봉인된 것을 가리키고, 투영 IR과 멤버 IR은 팬이 조합을 저장하는 순간 새로 만들어 봉인한다. 투영 IR은 발행 시각(as_of = known_at)을 기준으로 facts를 펼쳐, 이 조합에 실제 쓰인 스템의 사용 시간으로 역할별 기여 벡터와 권리 경로를 계산한 결과다. 이후 이 조합의 모든 정산은 이 네 IR만 입력으로 쓴다.

| 조합 | 만든 팬 | 1절 / 프리코러스 / 후렴 / 브리지 | 멤버 IR(비율) | 투영 IR digest | 멤버 IR digest |
| --- | --- | --- | --- | --- | --- |
| vc_dyn_001 | F1 | A / B / C / D | A·B·C·D 각 1/4 | `a296123d…` | `9f9ca3f1…` |
| vc_dyn_002 | F2 | A / A / B / B | A 1/2, B 1/2 | `af31688c…` | `9960d3d4…` |
| vc_dyn_003 | F3 | C / D / D / C | C 1/2, D 1/2 | `677a0ce8…` | `050cd63e…` |
| vc_dyn_solo(거부) | — | A / A / A / A | A 1 | 봉인 안 됨 | 봉인 안 됨 |

세 조합의 발행 봉인은 모두 같은 facts IR `8455359c…`와 정책 IR `c6ef08e3…`를 가리킨다. 다른 것은 투영 IR과 멤버 IR뿐이다.

A 한 명이 네 슬롯을 모두 부른 조합은 발행되지 않았다(`ISSUE_NOT_SETTLEABLE`). 실연 몫의 1인 상한 50%를 지킬 수 없어(`ALLOC_INFEASIBLE`) 정산할 수 없는 조합이므로, 코어가 발행 전에 막는다.

## 7~8단계: 이용 매출과 계산

구매 1건 3,300원은 권리자 풀 2,310원을 거쳐 권리자 8곳에 1원 단위로 나뉜다. 보컬리스트 몫은 맡은 구간 길이에 따라 달라진다.

**7. 이용 매출.** 3월 한 달 동안 팬들이 조합을 건당 3,300원에 소장 구매했다.

| 조합 | 구매 건수 | 매출(원) | 비고 |
| --- | --- | --- | --- |
| vc_dyn_001 | 300 | 990,000 | 4월 10일 환불 1건(−3,300) |
| vc_dyn_002 | 150 | 495,000 | — |
| vc_dyn_003 | 90 | 297,000 | 1건 이상거래 의심(FLAGGED) |
| 합계 | 540 | 1,782,000 | 환불 반영 순매출 1,778,700 |

**8. 구매 1건(vc_dyn_001, 3,300원) 계산.** 엔진이 낸 결과다.

| 단계 | 버킷 | 계산 | 금액(원) | 받는 사람 |
| --- | --- | --- | --- | --- |
| 1차 | 플랫폼 | 3,300 × 25% | 825 | 플랫폼 |
| 1차 | 운영 | 3,300 × 5% | 165 | 플랫폼 |
| 1차 | 권리자 풀 | 3,300 × 70% | 2,310 | 아래로 |
| 2차 | 마스터 | 2,310 × 40% | 924 | 레이블 L |
| 2차 | 실연 | 2,310 × 40% | 924 | 보컬리스트 A·B·C·D(아래 표) |
| 2차 | 작품 | 2,310 × 15% = 346.5 | 346 | 작가 W2 173, 신탁단체 C 173(W1 위임) |

작품과 소속사의 0.5원씩 남는 끝수 1원은 반올림 규칙에 따라 소속사에 배정됐고, 합계는 정확히 2,310원이다.

실연 924원의 보컬리스트별 분할(고정 40%는 멤버 비율 25%씩, 사용 60%는 구간 길이 140초 중 비중):

| 보컬리스트 | 맡은 슬롯(길이) | 고정분 | 사용분 | 합계(원) |
| --- | --- | --- | --- | --- |
| A | 1절(40초) | 92.4 | 158.4 | 251 |
| B | 프리코러스(20초) | 92.4 | 79.2 | 171 |
| C | 후렴(40초) | 92.4 | 158.4 | 251 |

| 받는 사람 | 금액(원) |

## 9~10단계: 정산, 원장, 지급

3월 정산은 조합별 run 3개가 모두 재계산 검증을 통과한 뒤 확정됐고, 권리자 8곳에 총 1,242,780원(원천징수 후 1,223,320원)이 지급됐다.

**9. 정산 배치(운영 백오피스 ⑥).**

1. 운영자(SPACE_OPS)가 3월 배치를 만들면 조합별 run 3개가 생긴다.
2. 엔진이 발행 봉인과 매출로 계산해 결과를 봉인하고, 독립 검증 워커가 다시 계산해 같은 digest인지 확인한다(3/3 VERIFIED).
3. 다른 사람(SPACE_SETTLE)이 확정하면 원장에 정산 분개(SETTLEMENT) 3건이 기록된다.
4. 이상거래 의심 1건은 플랫폼·운영 몫만 배분하고, 권리자 풀 2,310원은 조사 보류(FRAUD_REVIEW)로 묶는다.
5. 확정 뒤 들어온 환불 1건은 원 계산을 라인별로 정확히 되돌리는 역분개(REVERSAL)로 처리한다.

**10. 지급과 명세.** 5월 1일 지급 실행 결과다. 개인은 원천징수 3.3%(10원 미만 절사), 법인은 0%로 가정했다.

## 운영 백오피스 ⑧ 관제에 보이는 것

이 예시에서 관제 화면에 뜨는 신호는 다섯 가지이며, 플랫폼은 권리 내용을 바꾸지 않고 멈춤·보류·라우팅으로만 대응한다.

| 단계 | 신호 | 플랫폼의 대응 |
| --- | --- | --- |
| 발행 | 단독 조합 1건 거부(`ISSUE_NOT_SETTLEABLE`) | 거부 사유 집계, 팬앱 안내 문구 확인 |
| 수익 | 이상거래 의심 1건 | 권리자 풀 2,310원 자동 보류, ⑤ 신뢰안전 큐로 배정 |
| 정산 | run 3개 재계산 일치(불일치 0건) | 확정 가능 표시, ⑥ 정산 큐로 넘김 |
| 환불 | 확정 후 환불 1건 → 역분개 1건 | 원장 반영과 권리자별 음수 라인 확인 |
| 동의 철회(가정) | 보컬리스트 D 철회 → 판정 DENY | 영향 분석: D가 들어간 vc_dyn_001·003 노출 중지, 미정산 매출 보류, 권리자에게 통보 |

한 건 추적 예(구매 `ev_dyn_001_0001`):

1. 매출 3,300원 → 조합 vc_dyn_001(팬 F1)
2. 발행 봉인(S3, IR 4개 묶음): facts IR `8455359c…`, 정책 IR `c6ef08e3…`, 투영 IR `a296123d…`, 멤버 IR `9f9ca3f1…`(A·B·C·D 각 1/4)
3. 3월 정산 결과 IR(S4) `d0a66ff5…` → 라인 8개(레이블 924, A·C·D 각 251, B 171, W2 173, C 173, G 116)
4. 4월 10일 환불 → 역분개 `8a1c4f34…`(같은 라인 음수)
5. 5월 지급 `pay-2026-05`에서 순액으로 상계

## 재현 방법과 구현 공백

아래 명령으로 같은 결과를 다시 얻을 수 있다. 같은 입력이면 같은 digest가 나온다(두 번 실행한 보고서가 완전히 같았다).

```bash
cd 04_구현_소스코드
docker compose up -d
npm run scenario:dynamite -w rights-core -- --out ../../00_프로젝트_개요/예시_Dynamite
```

이 예시가 드러낸 구현 공백이다.

- [ ] 보컬리스트 동의의 저장·철회가 코어에 없다. 지금은 엔진 판정으로만 보여 준다.
- [ ] 이용허락 판정이 발행 게이트에 연결돼 있지 않다. 현재 발행은 팩 상태·분쟁·정산 가능 여부만 검사한다.
- [ ] 감상 매출(`TRAFFIC`)을 코어가 수집하지 않는다. 구독·광고 풀을 조합별 재생 비중으로 배정하는 단계도 필요하다.
- [ ] 실연자 앱이 없다. 명세는 코어 API로만 조회된다.
- [ ] 보컬리스트 D의 실연 위임(D → 소속사 G)은 이 정책에서 실연 몫 수령을 바꾸지 않았다. D의 몫은 D에게, G는 계약 몫 5%만 받았다. 위임을 실연 몫 수령에도 적용할지 정해야 한다.

이 공백은 [아키텍처 문서](시스템_아키텍처_및_업무분리안_20261012.md)의 "현재 구현과의 차이와 다음 작업" 목록에 합쳤다(동의 저장 2번, 발행 게이트 연결 3번, 위임 수령 결정 4번, 실연자 앱 11번, 감상 매출 13번).
