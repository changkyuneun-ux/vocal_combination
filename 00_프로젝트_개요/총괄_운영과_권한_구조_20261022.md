# 총괄 운영과 권한 구조(기능–권한–역할)

- 작성일: 2026-10-22
- 근거: [시스템 아키텍처 및 업무 분리안](시스템_아키텍처_및_업무분리안_20261012.md), [테넌트 관리 기준과 정책](테넌트_관리_기준과_정책_20261019.md), [MVP 진행계획](MVP_진행계획_Dynamite데모_20261016.md), [MVP 결정과 정책 고려사항](MVP_결정과_정책_고려사항_20261019.md)

## 요약

- MVP는 **총괄 한 사람이 한 앱·한 계정으로** 권리 등록부터 지급까지 끝까지 처리한다.
- 지금 흩어져 있는 역할 15종과 데모 계정 약 25개는 쓰지 않는다. 코드는 남겨 두고, 배포와 시드에서만 끈다.
- 권한 검사는 **기능 → 권한 → 역할**의 세 층으로 바꾼다. 역할과 역할–권한 매핑은 DB가 원본이다(RBAC). 그래서 나중에 역할을 나눌 때 코드를 고치지 않고 데이터만 바꾸면 된다.
- 테넌트 정책과 아키텍처 원칙은 그대로 지킨다. 총괄은 전역 슈퍼 계정이 아니다. 한 계정이 **플랫폼·권리 테넌트·참여 기관에 각각 소속**되고(TD9), 그 소속의 권한으로 일한다.
- 직무 분리는 규칙마다 모드를 둔다. MVP 총괄 운영에서는 `WAIVED`로 두고, 면제한 행위를 행·감사 로그·⑧ 신호에 남긴다. 기본값은 지금과 같은 `ENFORCE`다.

## 왜 바꾸나

| 지금 | 문제 |
| --- | --- |
| 역할 15종(`RIGHTS_EDITOR`, `EDITOR`, `WORK_APPROVER`, `ACTIVATOR`, `ISSUER`, `SPACE_OPS`, `SPACE_SETTLE`, `COMPLIANCE`, `LEGAL`, `TENANT_ADMIN`, `ONBOARDING`, `TRUST_OFFICER`, `PARTNER_INTEGRATION`, `PERFORMER`, `SYSTEM`) | MVP 단계의 사람 수(한 명)와 맞지 않는다 |
| 개발 계정 12개, 데모 페르소나 약 13개, 앱 5개(포털·운영·실연자·참여 기관·진행판) | 시연과 운영이 계정 전환과 앱 이동으로 흩어진다 |
| 코어의 `requireRole("SPACE_SETTLE")` 등 약 165곳, 화면 메뉴의 `roles: [...]` | 기능과 역할이 코드에 직접 묶여 있다. 역할을 바꾸려면 코드를 고쳐야 한다 |
| 직무 분리 7곳(서비스 검사, 그중 4곳은 DB CHECK도) | 한 사람으로는 흐름이 막힌다 |

## 점검 — 이 구조로 아키텍처·정책을 지키며 MVP가 진행되는가

판정: **지킬 수 있다.** 아래 표의 "조정" 열을 설계에 반영했다. 아키텍처 원칙에서 벗어나는 것은 두 가지다. 신뢰 경계별 앱 분리를 한 콘솔로 합치는 것(RD2), 직무 분리 면제(RD1)다. 둘 다 설정과 기록으로 범위를 묶었다.

### 아키텍처 문서와 대조

| 아키텍처 원칙 | 영향 | 조정 |
| --- | --- | --- |
| 코어 한 프로세스·한 DB, 판정·봉인·정산·원장을 한 트랜잭션에서 | 없음 | — |
| MDRL은 라이브러리, `engine-bridge`만 import, 봉인 digest | 서명(attestation)에 역할이 들어간다(`EDITOR`·`WORK_APPROVER`·`ACTIVATOR`·`SPACE_OPS`·`SPACE_SETTLE`) | 서명 자격은 **권한에서 뽑는다**(`policy.approve` → `WORK_APPROVER`). 봉인 형식·digest·Dynamite 금액은 바뀌지 않는다 |
| 독립 검증 워커는 다른 신원(`verified_by <> executed_by`) | 없음 | 시스템 무결성 장치라서 직무 분리 스위치 대상이 아니다. 항상 적용한다 |
| 멀티테넌시 RLS, 플랫폼 조회 통제(열람 기록·마스킹·break-glass) | 모든 권한을 가진 역할이 RLS를 우회할 위험 | RBAC는 "무엇을 하나"만 정하고 RLS(범위)는 건드리지 않는다. 총괄은 빅히트 데이터를 고칠 때 플랫폼 소속 + break-glass가 아니라 **빅히트 소속**으로 일한다 |
| 업무 시스템은 사용자 유형이 아니라 **권한 기준**으로 나눈다 | 이번 개편이 이 원칙을 코드로 옮긴다 | 권한에 업무 시스템(①~⑩)과 종류(결정·조회·개입)를 붙인다 |
| 권한의 세 구분: 결정은 권리자만, 플랫폼은 조회·개입만 | 총괄이 권리를 결정한다 | `decide` 종류의 권리 권한(①~③)은 참여 구분 `RIGHTS`의 역할에만 넣을 수 있다(DB 제약). 총괄은 빅히트 소속일 때만 결정할 수 있다 |
| "플랫폼 화면에는 권리 승인 버튼을 두지 않는다" | 콘솔 한 앱에 승인 화면이 함께 있다 | 메뉴와 버튼은 **현재 소속의 권한**으로만 보인다. 플랫폼 소속에서는 승인 버튼이 없다 |
| ④ 동의는 실연자 본인만 | 총괄이 대신하면 위반이다 | 대리 입력은 두지 않는다. 데모 환경에서 "실연자로 들어가기"로 그 멤버의 세션을 연다(행위자 = 멤버 본인, RD5) |
| 직무 분리는 서비스 검사와 DB 제약으로 이중 강제 | DB CHECK 4곳이 한 사람의 연속 행위를 막는다 | CHECK를 지우지 않는다. **면제 표시 열**(`sod_waived_rule`)이 있을 때만 통과하게 바꾸고, 그 열은 트리거가 규칙 모드가 `WAIVED`일 때만 허용한다(아래 "직무 분리") |
| 분리할 직무: 관제 ≠ 감사, 조사자 ≠ 판정자 | 아직 구현되지 않음 | 규칙 목록에 미구현 상태로 올린다. 역할을 나눌 때 같은 장치로 켠다 |
| 신뢰 경계에 따라 앱 4개, 운영은 SSO·IP 제한 뒤 | 콘솔 한 앱이 운영·포털·참여 기관 채널을 함께 쓴다 | 콘솔은 **운영 수준 보호**(IP 제한·TOTP·Secure 쿠키) 뒤에 둔다. 코어 채널 검사는 "현재 소속의 참여 구분 ↔ 채널"로 계속 지킨다(RD2). 앱 4개의 빌드는 그대로 남는다 |
| 위임 대행 업무함(`acting_on_behalf_of`) | 업무 → 역할 매핑이 코드에 고정(`RIGHTS_ENTRY → RIGHTS_EDITOR`) | 업무 → 권한 매핑을 데이터로 옮긴다 |

### 테넌트 정책과 대조

| 정책 | 조정 |
| --- | --- |
| TR4 권리는 당사자가 가진다, 한 계정 여러 역할 | 그대로. 총괄 계정은 당사자를 갖지 않는다 |
| TR5 플랫폼은 권리를 결정하지 않는다 | 권리 결정 권한은 `RIGHTS` 역할에만 넣을 수 있다. 총괄은 빅히트 소속으로 결정하고, 감사 로그에 소속(`acting_tenant_id`)이 남는다 |
| TR6 범위는 네 열쇠로만 정한다 | RBAC가 RLS를 바꾸지 않는다 |
| 6절·TN4 참여 구분별로 줄 수 있는 역할 | `role.org_class`, `permission.org_classes`. 맞지 않는 역할에 권한을 넣거나 맞지 않는 소속에 배정하면 거부한다 |
| 7절·TD7 수명주기 | 권한과 따로 둔다. 판정은 **권한 ∧ 조직 상태 ∧ 열쇠**다. 정지 상태의 "관리자 열람만"은 권한 `org.view_while_inactive`로 바꾼다 |
| 8절·TD4 조직 관리자는 자기 조직 역할만 주고, 자기 역할은 못 바꾼다 | `account.manage`는 현재 소속 안에서만 쓴다. 줄 수 있는 역할은 같은 참여 구분의 역할뿐이다. 자기 변경 금지(`SAME_PERSON`)는 유지한다 |
| 8절 운영은 개인 대신 동의·서명하지 못한다 | 대리 입력은 두지 않는다(RD5) |
| TD9 한 계정 여러 소속, 소속 전환 | 총괄 구성의 바탕으로 쓴다 |
| TD13 1인 테넌트 표준 템플릿 예외 | 정책 규칙의 모드 `TEMPLATE_EXEMPT`로 옮긴다(동작은 같음) |
| TN6 위임 대행 | 업무 → 권한 데이터(`delegable_task_permission`) |

### MVP 진행계획과 대조

| 원칙 | 조정 |
| --- | --- |
| 데모를 위한 별도 코드 경로를 만들지 않는다 | 총괄 운영은 데모 전용이 아니라 MVP 운영 방식이다. 데모에만 있는 것은 지금처럼 가상 데이터, 가상 공급자, 진행 도구(실연자 본인 전환 포함)뿐이다 |
| production은 가상 공급자를 거부한다 | 직무 분리 `WAIVED`도 같은 방식으로 다룬다. production 진입점은 `RC_SOD_WAIVER_ALLOWED=true`가 없으면 `WAIVED` 규칙이 있을 때 시작을 거부한다(RD1) |
| 페르소나 E2E(빅히트·멤버·운영이 각자) | 역할 템플릿을 배정한 다중 계정 시나리오는 시험으로 남긴다. 나중에 나눌 구조가 지금 동작하는지 계속 확인하기 위해서다 |

## 설계

### 1. 권한 모델(DB)

새 마이그레이션 `0039_rbac.sql`:

| 테이블 | 열 | 설명 |
| --- | --- | --- |
| `permission` | `perm_id`(예: `settlement.confirm`), `area`(①~⑩), `kind`(`decide`·`view`·`intervene`·`admin`), `org_classes`(쓸 수 있는 참여 구분 배열), `attest_role`(봉인 서명 자격, 없으면 NULL), `description` | 기능 단위 권한. 목록은 코드 상수(`platform/permissions.ts`)가 원본이고 마이그레이션·시작 시 맞춘다. 검사하는 쪽이 코드라서다 |
| `role` | `role_id`, `name`, `org_class`, `system`(수정 불가), `template`(배정 전 묶음) | 역할 |
| `role_permission` | `role_id`, `perm_id` | 트리거: `perm.org_classes`에 `role.org_class`가 없으면 거부 |
| `user_role` | `user_id`, `tenant_id`, `role_id` | 소속별 역할. 지금 `portal_role`을 대체한다(데이터 이전). 트리거: 소속 조직의 참여 구분 ≠ `role.org_class`이면 거부 |
| `delegable_task_permission` | `task`, `perm_id` | 위임 대행 업무 → 권한 |

**권한 목록 만드는 규칙:** 코어의 지금 역할 검사 한 곳 = (모듈, 행위) 하나 = 권한 하나. 같은 행위를 여러 처리기가 검사하면 권한 하나를 같이 쓴다. 영역별 예:

| 영역 | 권한 예 | 종류 | 참여 구분 |
| --- | --- | --- | --- |
| ① 권리 등록 | `rights.register`, `rights.claim`, `document.upload`, `confirmation.request` | decide | RIGHTS (플랫폼 위탁 당사자 등록 `party.register_platform`은 PLATFORM) |
| ② 정책·팩 | `policy.edit`, `policy.approve`, `policy.activate`, `pack.activate` | decide | RIGHTS |
| ③ 발행 | `issuance.view`, `issuance.issue` | view·decide | RIGHTS |
| ⑤ 무결성 | `validation.accept_request`, `validation.accept`, `audio.review`, `dispute.handle` | intervene | PLATFORM |
| ⑥ 정산·재무 | `revenue.ingest_review`, `settlement.run`, `settlement.confirm`, `payout.profile_set`, `payout.run`, `statement.view` | intervene·view | PLATFORM (`statement.view`는 RIGHTS·PARTICIPANT도) |
| ⑦ 관리·감사 | `tenant.onboard`, `tenant.status`, `account.manage`, `audit.view`, `breakglass.open`, `rbac.manage`, `sod.manage` | admin | 항목마다 |
| ⑧ 관제 | `pipeline.view`, `trace.view`, `impact.view` | view | PLATFORM |
| 계약 | `contract.template_author`, `contract.template_approve`(법무), `contract.sign_org` | decide·admin | 항목마다 |
| 연결 | `link.propose`, `link.confirm` | decide | RIGHTS·PARTICIPANT·PLATFORM |
| 참여 기관 | `trust.works_view`, `partner.report_upload` | view·intervene | PARTICIPANT |
| 개인 | `self.consent`, `self.identity`, `self.dispute` | decide | INDIVIDUAL |

**역할 시드**

| 역할 | 참여 구분 | 종류 | 권한 |
| --- | --- | --- | --- |
| `PLATFORM_ALL` | PLATFORM | system | PLATFORM에 쓸 수 있는 모든 권한 |
| `RIGHTS_ALL` | RIGHTS | system | RIGHTS에 쓸 수 있는 모든 권한(관리자 포함) |
| `PARTICIPANT_ALL` | PARTICIPANT | system | PARTICIPANT에 쓸 수 있는 모든 권한 |
| `PERFORMER` | INDIVIDUAL | system | `self.*` |
| `SYSTEM` | PLATFORM | system | 수집·정산 실행·검증(시스템 신원 전용, 사람에게 배정 불가) |
| 지금 역할 13종(`RIGHTS_EDITOR` … `PARTNER_INTEGRATION`) | 각자 | template | 지금 검사와 같은 권한 묶음. 아무에게도 배정하지 않는다. 나중에 역할을 나눌 때 출발점이 되고, 다중 계정 시험이 쓴다 |

### 2. 검사

- 로그인·소속 전환 때 `loadActor`가 그 소속의 권한 집합을 `actor.permissions`에 담는다. `actor.roles`는 화면 표시용으로만 남는다.
- `requireRole`·`requireAnyRole`·`roles.has` 약 165곳을 `requirePermission(actor, perm)`으로 바꾼다. 거부 코드는 지금처럼 403 `FORBIDDEN`이고 메시지에 권한 이름이 들어간다.
- 판정 순서: 채널(참여 구분) → 권한 → 조직 상태(수명주기) → 직무 분리 → RLS. 앞의 셋이 서로를 대신하지 않는다.
- 봉인 서명: 서명할 때 쓴 권한의 `attest_role`을 attestation의 역할로 적는다.
- 화면: 메뉴 `roles: [...]`를 `perm: "..."`로 바꾼다. 세션 응답(`/auth/me`)이 현재 소속의 권한 목록을 준다.

### 3. 총괄 구성

- 계정 `usr_admin`(총괄) 하나, 운영 수준 로그인(비밀번호 + TOTP)
- 소속 세 개:

| 소속 | 역할 |
| --- | --- |
| 플랫폼 운영 | `PLATFORM_ALL` |
| 빅히트 뮤직(권리 테넌트) | `RIGHTS_ALL` |
| 가상 신탁단체(참여 기관) | `PARTICIPANT_ALL` |

- 새 권리 테넌트를 등록하면 총괄을 그 테넌트의 첫 관리자로 넣을 수 있다(온보딩 화면의 선택 항목). 실제 고객 관리자를 초대하는 지금 경로도 그대로 둔다.
- 마지막 `PLATFORM_ALL` 보유자는 역할을 회수하거나 잠글 수 없다.

### 4. 총괄 콘솔

- 주소 `console.dobedupop.localhost`, 백오피스 코드베이스의 새 빌드 `VITE_APP=console`
- 운영·포털·참여 기관 화면 코드를 그대로 쓴다. **현재 소속의 참여 구분**에 따라 메뉴 묶음이 바뀐다(플랫폼 → 운영 메뉴, 권리 테넌트 → 포털 메뉴, 참여 기관 → 참여 기관 메뉴). 각 메뉴는 권한으로 다시 거른다.
- 머리글: 소속 전환(지금 `/auth/switch`), 현재 소속 배지, "실연자로 들어가기"(데모 환경 전용)
- 게이트웨이: console 호스트는 `/api/ops`·`/api/portal`·`/api/partner`를 통과시키고 운영 IP 제한과 보안 헤더를 적용한다
- 세션: console 채널로 발급되고 세 채널에서 유효하다. 요청마다 코어가 **채널 ↔ 현재 소속의 참여 구분**을 검사한다(`CHANNEL_FORBIDDEN`). 예를 들어 빅히트 소속 상태로 `/api/ops`를 부르면 403이다
- 실연자로 들어가기: 데모 환경의 페르소나 빠른 로그인(이미 있는 장치)으로 그 멤버의 `artist.` 세션을 새 탭에 연다. production 진입점에는 없다

### 5. 직무 분리

`sod_rule` 테이블(규칙 id, 설명, 모드, 바꾼 사람·시각). 모드는 셋이다.

- `ENFORCE`: 지금처럼 같은 사람의 연속 행위를 거부한다
- `TEMPLATE_EXEMPT`: 정책 규칙에만 있다. TD13 동작이다
- `WAIVED`: 같은 사람도 허용하고 면제를 기록한다

| 규칙 | 지금 검사 | DB CHECK |
| --- | --- | --- |
| `policy.edit-approve-activate` | `policy/service.ts` | 없음(서명 PK) |
| `settlement.run-confirm` | `settlement/service.ts` | `settlement_batch` |
| `contract-template.author-approve` | `contracts/service.ts` | `contract_template` |
| `policy-template.author-approve` | `policy/templates.ts` | `policy_template` |
| `validation.request-approve` | `validation/service.ts` | `validation_issue` |
| `link.propose-confirm` | `participants/links.ts` | 없음 |
| `payout.account-run` | `payout/policy.ts`(보류 사유 `ACCOUNT_SOD`) | 없음 |
| `monitor.observe-audit`, `integrity.investigate-judge` | 미구현 | — |

규칙 밖으로 항상 적용하는 것: 독립 검증(`verified_by <> executed_by`), 자기 역할 변경·자기 잠금 금지, 본인 동의(`NOT_SELF`)

**면제 기록과 DB 이중 강제**
- CHECK가 있는 표에 `sod_waived_rule` 열을 더한다. CHECK는 `(confirmed_by <> executed_by) OR sod_waived_rule IS NOT NULL` 꼴로 바꾼다.
- 트리거가 `sod_waived_rule`의 규칙이 그 순간 `WAIVED`인지 확인한다. 아니면 거부한다. 그래서 앱 코드가 열을 잘못 채워도 DB가 막는다.
- 서비스는 같은 사람이면 규칙 모드를 읽어 `ENFORCE`면 거부(지금 코드), `WAIVED`면 열을 채우고 감사 `SOD_WAIVED`(규칙·대상·사람)를 남긴다.
- ⑧ 관제 신호 "직무 분리 면제 중인 규칙 수·최근 면제 행위"를 추가한다.
- 모드 변경은 `sod.manage` 권한이 필요하고 감사에 남는다. `WAIVED`로 바꾸는 것은 환경 설정이 허용할 때만 된다(RD1).
- 기본값: 마이그레이션은 모두 `ENFORCE`(TD13 규칙은 `TEMPLATE_EXEMPT`)다. 데모 시드와 MVP 운영 설정에서만 `WAIVED`로 바꾼다. 기존 시험은 기본값으로 돌므로 그대로 통과해야 한다.

### 7. 역할·권한 관리 화면

- 위치: ⑩ 관리 → 역할·권한(플랫폼 소속, `rbac.manage`)
- 역할 목록(참여 구분·시스템·템플릿 표시), 역할별 권한 체크(그 참여 구분에 쓸 수 있는 권한만), 새 역할 만들기, 계정별·소속별 역할 배정, 직무 분리 규칙 모드(`sod.manage`)
- 시스템 역할은 수정할 수 없다. 변경은 모두 감사에 남는다.
- 포털·참여 기관의 "담당자 계정"은 지금처럼 조직 관리자가 쓰고, 고를 수 있는 역할은 그 참여 구분의 역할(템플릿 포함)이다.

## 바뀌지 않는 것(완료 기준에 포함)

- Dynamite 금액: 소속사 2,285,920 · 레이블 2,030,952 · 작가 각 296,604 + 원천징수 83,650
- 봉인 digest(facts·정책·조합 지분·멤버·매출·결과·manifest). 서명(attestation)의 서명자 id는 바뀐다
- 테넌트 격리 시험(빅히트가 작가 명세를 못 봄, 멤버는 포털 불가, 빅히트 소속은 운영 채널 불가)
- 기존 코어·화면·E2E 시험(기본 모드 `ENFORCE`에서)

## 시험

- 권한 목록 ↔ 코어 검사 지점 대조: 모든 처리기가 권한 하나 이상을 검사하거나 공개·본인 전용임을 표시한다(누락이 있으면 시험 실패)
- 역할 템플릿 = 지금 역할: 템플릿을 배정한 다중 계정 시나리오가 지금과 같은 결과를 낸다
- 참여 구분 제약: `RIGHTS` 결정 권한을 `PLATFORM` 역할에 넣기, `RIGHTS_ALL`을 플랫폼 소속에 배정하기 → 거부
- 직무 분리: 규칙마다 `ENFORCE`면 거부, `WAIVED`면 통과 + `sod_waived_rule` + 감사, 모드가 `ENFORCE`인데 열을 직접 채우면 DB 거부, production 진입점의 `WAIVED` 거부
- 총괄 1인 E2E(데모 스택): `usr_admin` 하나로 콘솔에서 Dynamite 전 단계 → 같은 금액. 실연자 단계는 본인 전환
- 채널 ↔ 소속: 빅히트 소속으로 `/api/ops` 403, 플랫폼 소속으로 정책 승인 403
