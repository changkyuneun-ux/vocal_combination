# dobedubpop 시스템 아키텍처 및 업무 분리안

- 작성일: 2026-10-12
- 원본(공유 문서): https://claude.ai/code/artifact/9db7d516-16a3-4822-a995-ea0671a5fba3

**사용자 관점.** 참여자는 각자 자기 앱에서 자기 일만 한다. 권리자는 권리자 포털에서 권리를 등록하고 분배 규칙을 승인하며, 보컬리스트는 실연자 앱에서 동의하고 수익을 확인하고, 팬은 팬 앱에서 허락된 범위 안에서 조합하고 감상한다. 플랫폼 운영자는 운영 백오피스에서 권리 생성부터 지급까지의 흐름을 지켜보고 문제를 처리하지만, 권리를 대신 결정하지 않는다.

**서비스 안정성 관점.** 돈과 권리를 다루는 권리 및 정산 코어는 하나로 묶어, 판정·봉인·정산·원장을 한 데이터베이스의 한 트랜잭션 안에서 처리한다. 그래서 금액이 어긋나거나 중복 지급되지 않는다. 오디오 처리나 외부 연동처럼 무겁거나 실패가 잦은 일은 처리·연동 서비스로 떼어내, 그쪽 장애가 코어와 사용자 화면으로 번지지 않게 한다.

권리 생성부터 지급까지 실제 코드로 돌린 예시는 [예시: Dynamite 2차 이용](예시_Dynamite_2차이용_권리생성에서_지급까지_20261012.md)에 있다.

## 아키텍처 한눈에

모든 채널은 게이트웨이를 거쳐 들어오고, 권리 판정·발행 봉인·정산·원장은 권리 및 정산 코어 안에서만 확정된다. 사용자 서비스와 처리·연동 서비스는 코어의 원본을 직접 쓰지 않는다.

## 구조 결정과 근거

권리 및 정산 코어(권리 판정·발행 봉인·정산·원장)는 하나의 프로세스와 하나의 PostgreSQL에 둔다. 돈과 권리가 같은 트랜잭션 안에서 정합해야 하기 때문이다.

- **MDRL은 라이브러리로 호출한다.** 네트워크 서비스로 만들면 결정성(같은 입력 → 같은 digest)이 흔들린다. MDRL을 import하는 곳은 `engine-bridge` 하나뿐이다.
- **원본 데이터는 데이터베이스에 있다.** IR은 이 데이터로 만든 JSON 문서이고, 모든 정산은 데이터베이스가 아니라 IR 문서를 읽어 계산한다.
- **비동기는 Outbox + pg-boss로 처리한다.** 상태 변경과 Outbox 기록을 한 트랜잭션에 쓰고 워커가 이어받는다.

**IR 문서는 언제 만들고 어떻게 쓰나.** 정책 컴파일, 조합 발행, 정산 때 데이터베이스에서 필요한 내용을 읽어 IR 문서를 만든다. 문서에는 내용으로 계산한 해시(digest)를 붙여 저장하고, 저장한 문서는 수정·삭제할 수 없다. 조합의 정산은 그 조합이 발행될 때 만든 IR 문서를 읽는다. 그래서 발행 뒤에 데이터베이스의 권리 정보가 바뀌어도, 이미 발행된 조합의 정산 금액은 바뀌지 않는다.

| 효과 | 내용 |
| --- | --- |
| 재현 | 같은 사본이면 언제 다시 계산해도 같은 금액이 나온다 |
| 검증 | 독립 검증 워커나 외부 파트너가 같은 사본으로 다시 계산해 확인한다 |
| 분쟁 대응 | "이 번호의 사본으로 계산했다"고 금액의 근거를 증명한다 |

**IR 문서의 저장 형태.** IR 문서 하나는 내용을 담은 JSON 파일 하나와, 그 파일을 설명하는 `sealed_document` 행 하나로 저장된다. 둘은 digest로 연결된다. digest는 봉인 본문을 JCS(RFC 8785)로 정규화한 바이트의 SHA-256이고, 앞에 `mdrl:sha256:`을 붙인다.

| 구분 | 저장 위치 | 내용 |
| --- | --- | --- |
| 물리 파일(정본) | blob 저장소. 개발 환경은 로컬 파일시스템(`rights-core/.blobs/`, `BLOB_DIR`로 변경), 운영은 오브젝트 저장소 | 봉인 본문의 정규화 바이트. 파일 이름은 `<digest hex 64자>.json`이고, 앞 2자리와 다음 2자리로 폴더를 나눈다(예: `2e/77/2e77bb42….json`). 임시 파일에 쓴 뒤 rename으로 바꿔, 반쯤 쓰인 파일이 남지 않는다 |
| 메타데이터 | PostgreSQL `sealed_document` 행 | `digest`(PK), `kind`(facts·allocation·projection·members·events·allocation_result·reversal_result·manifest), `doc_id`, `doc_version`, `format`, `byte_size`, `storage_uri`(파일 위치), `content`(64KiB 이하일 때만 넣는 JSONB 조회용 사본), `created_at` |

- **수정·삭제할 수 없다.** `sealed_document`는 트리거로 UPDATE·DELETE를 막고, 앱 계정에는 SELECT·INSERT 권한만 준다. 같은 digest는 한 번만 저장된다. 그래서 내용이 같은 IR은 하나로 합쳐진다(예: 멤버 비율이 같은 두 조합은 멤버 IR 행 하나를 같이 쓴다).
- **읽을 때마다 digest를 다시 계산해 확인한다.** JSONB 사본이 있으면 사본을, 없으면 파일을 읽는다. 다시 계산한 digest가 다르면 `SEAL_CORRUPT` 오류를 내고 정산을 멈춘다.
- **다른 테이블은 본문을 복사하지 않고 digest만 가리킨다.** `policy_version`(정책·facts), `issue_seal`(facts·정책·조합 지분·멤버), `settlement_run`(매출·결과), `reversal_run`(역분개 결과), `settlement_batch`(배치 manifest), `attestation`(역할별 Ed25519 서명)이 모두 `sealed_document`를 외래키로 참조한다.
- **봉인 본문에서 빼는 것이 있다(결정 2026-10-15).** 조합 지분·정산 결과·역분개 결과 IR은 자기 digest 필드(`digest`, `result_digest`)를 품는다. 이 IR들은 그 필드와 설명 자료 `trace`를 뺀 나머지를 봉인한다. 그래서 정산 run이 가리키는 digest와 IR 안의 `result_digest`가 같은 값이다. 읽을 때 자기 digest 필드는 다시 붙여 돌려주고, `trace`는 저장하지 않는다. `trace`는 계산 과정을 설명하는 자료일 뿐이고, 필요하면 같은 입력으로 다시 계산해 얻는다. 이렇게 하면 결과 IR이 작아진다(Dynamite 원곡 배치 조합의 결과 IR이 1.9MB에서 0.8MB로 줄었다).

| 예(Dynamite) | kind | 행 수 | 파일 크기 | JSONB 사본 |
| --- | --- | --- | --- | --- |
| facts IR | facts | 1 | 20.7KB | 있음 |
| 정책 IR | allocation | 1 | 992B | 있음 |
| 조합 지분 IR | projection | 4 | 약 3.8KB | 있음 |
| 멤버 IR | members | 3(조합 4개 중 2개가 같은 IR) | 110~175B | 있음 |
| 매출 IR | events | 4 | 18~110KB | 64KiB를 넘는 1건은 없음 |
| 정산 결과 IR | allocation_result | 4 | 135~817KB | 없음(파일만) |
| 역분개 결과 IR | reversal_result | 1 | 1.3KB | 있음 |
| 배치 manifest | manifest | 1 | 389B | 있음 |

조합 지분 IR은 한 조합에서 역할별로 누가 몇 분의 몇을 갖는지(원천 지분이 조합 단위로 바뀐 2차 권리)를 담는다. 이전 이름은 "투영 IR"이고, 식별자(`kind = projection`, 형식 태그 `mdrl-projection/1`, `issue_seal.projection_digest`)는 봉인 digest와 재계산 대조를 지키려고 그대로 두었다(용어 결정 2026-10-15).

미구현: 운영용 오브젝트 저장소 구현은 아직 없다(저장소 인터페이스가 `put`·`get` 두 함수라 구현만 추가하면 된다). 또 파일을 DB 행보다 먼저 쓰기 때문에, 트랜잭션이 롤백되면 DB 행 없는 파일이 남는다(Dynamite 실행에서 발행이 거부된 조합의 파일 2개). 내용 주소라 정합성에는 영향이 없지만 정리 작업이 필요하다(다음 작업 15번).
| 변경 격리 | 표가 바뀌어도 이미 확정된 거래의 근거는 바뀌지 않는다 |

코어 밖으로 떼어낼 것은 부하나 장애 성격이 코어와 다른 다섯 가지다.

| 분리 대상 | 분리 이유 | 코어와의 경계 |
| --- | --- | --- |
| 오디오 처리 서비스 (스템 기술 검수·소스 출처 검사·조합 렌더링) | CPU·GPU를 많이 쓰고 실패가 잦다 | 작업 큐로 요청, 결과만 코어에 기록 |
| 연동 허브 (DDEX·유통사 CSV·PSP 웹훅·파트너 API) | 외부 포맷이 코어 모델을 오염시키지 않게 번역한다 | 원본 해시 보관, 거부 큐, 정규화된 이벤트만 전달 |
| 조합 빌더 API와 판정 캐시 | 조합 후보가 수십만~백만 단위이고 팬 트래픽은 읽기 위주다 | 캐시 키에 활성 정책 digest 포함, 동의 철회·스템 오디오 변경 시 그 보이스·스템을 쓴 판정만 무효화(곡별 세대 번호로 경합 방지). 판정은 안내용이고 발행 봉인은 코어에서만 만든다 |
| 독립 검증 워커 | 정산 결과를 다른 신원으로 재계산해야 검증의 의미가 있다 | 실행 워커와 다른 서비스 계정, 불일치 시 run VOID |
| 읽기 모델 (권리 지도·명세·대시보드) | 조회 형태가 다양하고 원본에서 언제든 재생성할 수 있다 | 원본을 쓰지 않음, 그래프 DB는 탐색 병목이 실측될 때만 도입 |

**멀티테넌시.** 테넌트는 포털에 로그인해 일하는 조직 단위다(레이블·기획사·출판사·신탁단체·파트너·플랫폼 운영, 팬은 플랫폼 기본 테넌트). 테넌트는 데이터를 볼 수 있는 범위를 정하는 단위이고, 정산 금액은 테넌트가 아니라 파티(권리 주체)에 귀속된다. 모든 테넌트가 데이터베이스 하나를 같이 쓰고, PostgreSQL 행 단위 보안(RLS)으로 다른 테넌트의 행을 데이터베이스가 직접 걸러낸다. 앱 코드가 조회 조건을 빠뜨려도 다른 테넌트의 데이터는 반환되지 않는다.

| 데이터 | 볼 수 있는 테넌트 | 예(Dynamite) |
| --- | --- | --- |
| 소유 데이터: 곡·녹음·스템·팩·정책·계약 | 등록한 테넌트(`owner_tenant_id`)만 열람·수정 | 빅히트 뮤직(레이블)이 등록한 팩 DYNAMITE-FAN은 빅히트 뮤직(레이블)만 수정한다 |
| 참여 데이터: 정산 라인·명세·지급 | 해당 파티가 소속된 테넌트만 열람 | 작가 David Stewart 몫의 정산 라인은 David Stewart가 소속된 테넌트만 본다 |
| 운영 조회 | 운영 백오피스가 ⑧ 관제의 단계별 통제(마스킹·사유 기록)를 거쳐 전 테넌트 조회 | 이상거래 조사 때 관련 팩을 조회한다 |

한 곡에 여러 테넌트의 파티가 권리를 나눠 가져도, 다른 테넌트의 계약·지분 상세는 볼 수 없다.

구현(2026-10-15, `rights-core/migrations/0017_tenancy.sql`)은 이렇게 동작한다.

- **요청 범위.** HTTP 요청은 트랜잭션 시작 때 행위자의 범위를 설정한다. 플랫폼 운영 테넌트 사용자는 `platform`(전체), 그 밖의 사용자는 `tenant`(자기 테넌트)다. 워커와 내부 호출은 `system`(전체)으로 돈다. 범위가 설정되지 않은 연결은 아무 행도 보지 못한다.
- **소유 데이터 쓰기.** 다른 테넌트가 소유한 곡·녹음·범위 밑에 녹음·스템·주장을 붙이려 하면 RLS가 거부한다(403 `TENANT_FORBIDDEN`).
- **곡 전체가 필요한 계산.** facts 봉인은 다른 테넌트가 기록한 주장까지 담아야 하므로, 범위 행을 요청자 범위에서 확인한 뒤 행 조회만 system 범위로 한다. 결과는 봉인되어 digest로만 노출된다.
- **봉인 조회.** 봉인은 내용 주소라 소유자가 없다. 요청자가 볼 수 있는 행(정책 버전·발행 봉인·정산 run 등)이 그 digest를 가리킬 때만 내용을 돌려준다.
- **운영 데이터.** 매출·정산 run·풀·보류·격리 같은 플랫폼 운영 테이블은 테넌트 범위에서 읽을 수 없다.
- **플랫폼 조회의 단계별 통제(구현 2026-10-15, `0019_inspection.sql`).** 플랫폼은 전부 읽을 수 있지만 권리 오너가 아니므로 세 단계로 통제한다.
  - 1단계 열람 기록: 운영 채널에서 다른 테넌트의 레코드 상세(범위·정책·팩·발행·동의·명세·지급)를 열면 같은 트랜잭션에서 `inspection_audit_log`에 남는다. 목록·집계와 플랫폼 자기 데이터는 남기지 않는다.
  - 2단계 개인정보 마스킹: 지급 계좌 토큰은 끝 4자만 보인다. 원문은 정산 담당이 사유를 적어야 보이고, 해제 기록이 응답과 같은 트랜잭션에 남는다.
  - 3단계 break-glass: 플랫폼이 테넌트 소유 권리 데이터를 바꾸려면 대상 테넌트·사유·최대 60분의 긴급 권한을 연다. RLS 쓰기 정책(`rc_can_write`)이 이것 없이는 테넌트 소유 행과 그 밑의 새 행 쓰기를 거부하고, 열려 있는 동안 만든 행은 대상 테넌트 소유가 된다.
  - 투명성: 테넌트는 권리자 포털에서 자기 테넌트를 대상으로 한 열람 기록과 break-glass를 본다.

## 오디오 처리 서비스

오디오 파일을 직접 다루는 일은 한 서비스로 모으되, 성격이 다른 세 기능으로 나눈다. 이 서비스는 권리를 판단하지 않고 기술 신호만 만들며, 스템을 사용 가능(READY)으로 바꾸거나 발행을 허용하는 결정은 권리 및 정산 코어가 내린다.

| 기능 | 언제 | 하는 일 | 결과(코어에 기록) | 실패·의심 시 |
| --- | --- | --- | --- | --- |
| 스템 기술 검수(QC) | 권리자 포털에서 스템 업로드 직후 | 포맷(샘플레이트·비트 깊이), 클리핑(True Peak), 무음, 라우드니스(LUFS), 파일 해시 측정 | `stem.qc_status`, `qc_fail_code` | 운영 백오피스 ⑤ 자동 QC 실패 큐 → 재업로드 요청 |
| 소스 출처 검사 | 업로드 직후(QC와 병행) | 상용 음원 대조(음향 지문), AI 생성 판별, 등록 가창자 음성 대조, 메타데이터(ISRC·크레딧) 정합 | `source_integrity_check`: PASS·SELF_MATCH·REVIEW·BLOCK | ⑤ 소스 무결성 검사 큐 → 권리자 소명. 통과하지 못하면 스템 READY 불가 |

**구현(2026-10-15, 스템 기술 검수·소스 출처 검사).** `audio-service` 패키지가 오디오 처리 서비스다. HTTP 서비스(`POST /analyze`)로 띄우거나 코어가 라이브러리로 부른다.

- 이 서비스는 ffmpeg로 포맷·True Peak·무음·라우드니스(EBU R128)를 재고, 파일 해시와 음향 지문을 만든다. 음향 지문은 300~3000Hz 16대역의 에너지 변화를 11.6ms 간격으로 적는 방식이다.
- 권리자 포털·운영에서 스템 오디오를 올리면 코어가 원본을 내용 주소 저장소에 두고 검사 작업(`audio-check`)을 큐에 넣는다. 워커가 서비스의 신호를 받아 소스 출처를 판정하고 `stem_audio.status`를 정한다.
  - 상용 참조 음원(`reference_audio`)과 지문이 맞는 경우: 같은 권리자의 음원이면 SELF_MATCH, 다른 권리자의 음원이면 BLOCK.
  - 다른 녹음과 같은 파일이거나, 파일이 슬롯보다 짧은 경우: REVIEW.
- 상태는 READY, QC_FAILED, REVIEW, BLOCKED 중 하나다. REVIEW는 운영(⑤ 오디오 검수 큐)이 사유를 적어 READY나 BLOCKED로 정한다. READY가 아닌 스템은 발행 게이트가 거부한다(`STEM_NOT_READY`).
- 다시 인코딩하고 앞을 잘라도 같은 음원은 유사도 0.96 이상, 다른 음원은 0.65 이하로 측정됐다. 판정 기준은 0.85다.
- 오디오 없이 메타데이터만 등록한 스템(시험·시연용)은 검사 대상이 아니다.
- 아직 없는 것: AI 생성 판별, 등록 가창자 음성 대조. 판정에 쓰지 않고 `notChecked`로 남긴다.

**구현(2026-10-15, 조합 렌더링).** `audio-service`의 렌더러가 슬롯별 스템과 반주를 서버에서 믹스다운한다.

- **미리듣기:** 팬 앱 `/fan/previews`가 발행 전에 앞 5초를 MP3로 만들어 준다. READY 오디오가 있는 스템만 쓸 수 있다.
- **마스터:** 발행 직후 `render-master` 작업이 전체를 WAV 48kHz/24비트로 만든다. 리미터를 걸고, 조합마다 다른 워터마크를 넣는다. 워터마크는 17.0·17.5kHz FSK이고, ID는 `wm_<발행 봉인 id>`다.
- **렌더 결과 다운로드:** 발행한 팬 본인만 받는다. 원본 스템은 내보내지 않는다.
- **렌더 무결성 검증(운영):** 봉인된 스템 배정으로 다시 렌더해 해시를 비교하고, 저장된 마스터에서 워터마크를 읽는다. 결과는 MATCH, MISMATCH, WATERMARK_MISSING 중 하나다. 같은 입력이면 같은 바이트가 나오므로, 발행 뒤 스템 오디오가 바뀌면 MISMATCH로 드러난다.
- **오디오가 없는 스템:** 메타데이터만 등록된 스템이 섞인 조합은 렌더를 건너뛴다(SKIPPED).
- **미구현:** DRM과 반출용 워터마크(`export_watermark_id`)는 다운로드·상업 이용 스탬프가 생길 때 붙인다. 워터마크는 무손실 마스터에서만 읽힌다(손실 압축이 이 대역을 깎을 수 있다).

- **원본 스템은 밖으로 내보내지 않는다.** 마스터 권리자 계약 조건(서버사이드 렌더링 한정·반출 금지)에 따라 팬 앱에는 렌더 결과만 보낸다.
- **다운로드·상업 이용 스탬프**가 발급되면 반출용 워터마크(`export_watermark_id`)를 새로 넣어, 외부 유출 시 발급 건과 조합·발행 봉인까지 역추적한다.
- **정산 계산은 렌더 결과를 쓰지 않는다.** 정산의 사용량(구간 길이)은 발행 봉인에 기록된 스템 배정에서 나온다.

'핑거프린트'·'지문'이 서로 다른 것을 가리켜 혼동되므로 아래 이름으로 구분하고, 설계 문서(데이터모델 v2.8, UI 가이드 v1.6, IA, 조합제약·검증·코어규격 설계)도 이 이름으로 맞췄다. 컬럼 이름 같은 식별자는 그대로 두었고, 봉인 digest(`mdrl:sha256:…`)는 지문이라 부르지 않는다.

| 부르는 이름 | 식별자(그대로 유지) | 무엇인가 | 만드는 곳 |
| --- | --- | --- | --- |
| 음향 지문 | `FINGERPRINT_MATCH` | 소리에서 뽑은 지문. 업로드한 스템이 기존 상용 음원인지 대조한다 | 오디오 처리 서비스(소스 출처 검사) |
| 조합 구성 해시 | `fingerprint_hash`, `content_fingerprint` | 스템 버전·구간·믹스 설정·렌더 엔진 버전을 정규화한 해시. 소리가 아니라 구성으로 만든다 | 권리 및 정산 코어(발행·유일키 검사) |
| 반출 지문 참조 | `rights_stamp.fingerprint_ref` | 다운로드·상업 이용으로 반출된 음원을 나중에 식별하기 위한 참조 | 오디오 처리 서비스(렌더링)가 만들고 코어에 기록 |

현재 구현에는 세 기능이 모두 없다. 코어(`rights-core`)의 스템 테이블에는 파일·QC·렌더 정보가 없다.

## 연동 허브

연동 허브는 외부 형식을 코어 모델로 번역하는 경계다(구현 2026-10-15). 외부 형식이 코어 모델에 섞여 들어오지 않도록 번역과 적용을 나눈다.

- **번역(`integration-hub` 패키지).** 파일 바이트를 받아 정규화 레코드 세 가지(판매 `SALE`, 환불 `REFUND`, 감상 매출 `STREAM_REVENUE`) 또는 줄별 거부 사유로 바꾸는 순수 함수다. 데이터베이스와 코어 모델을 모른다.
- **적용(코어 `hub` 모듈).** 원본 파일을 그대로 보관하고(SHA-256, 바이트), 정규화 레코드만 매출 이벤트로 넣는다. 판매는 `PURCHASE`, 환불은 원거래 이벤트의 `REFUND`, 감상 매출은 `TRAFFIC`이다.

| 형식 | 읽는 것 | 파일 단위 거부 |
| --- | --- | --- |
| 유통사 CSV | 머리글 있는 CSV(열 순서 자유). `transaction_id`, `type`, `asset_id`, `amount_krw`, `occurred_at`, 환불이면 `original_transaction_id` | 필수 열 없음 |
| DDEX DSR(부분 집합) | 탭 구분 평면 파일의 HEAD·SU01·FOOT. 이용 유형이 소장(PermanentDownload)이면 판매, 스트리밍이면 감상 매출. 다른 레코드는 건너뛴다. 인증된 DSR 구현이 아니다 | HEAD·FOOT 없음, FOOT 건수 불일치(잘린 파일) |

- **줄별 결과.** 각 줄은 적용(ACCEPTED)·중복(DUPLICATE, 이미 받은 거래)·거부(REJECTED) 중 하나로 남는다. 파일 단위 오류가 있으면 아무 줄도 적용하지 않는다.
- **멱등.** 같은 파일을 다시 보내면 처음 결과를 돌려준다. 다른 파일에 같은 거래가 다시 오면 같은 내용은 중복, 다른 내용은 거부(`IDEMPOTENCY_MISMATCH`)다. 매출 이벤트 id는 테넌트와 거래 id의 해시라 재전송·재처리에도 같다.
- **거부 큐.** 거부된 줄이 거부 큐다. 고칠 수 있는 사유(`UNKNOWN_ASSET` 자산 대응 없음, `UNKNOWN_ORIGINAL` 원거래 미도착, `NOT_ISSUED` 미발행)는 고친 뒤 운영이 재처리한다. 저장된 정규화 레코드로 다시 적용하고, 원본 파일은 바뀌지 않는다. 형식 오류나 정책 불일치(`POLICY_NO_TRAFFIC`)는 재처리 대상이 아니다.
- **자산 대응.** 파트너는 조합을 자기 자산 id(ISRC·상품 코드)로 부른다. 플랫폼이 외부 유통을 열 때 자산 id와 조합의 대응(`partner_asset`)을 등록한다.
- **격리.** 파트너는 RLS로 자기 테넌트의 파일·줄·대응만 본다.
- **화면.** 운영 백오피스 "연동 허브"(파일·줄별 결과·재처리·자산 대응)와 "감상 수익 풀". ⑧ 수익 단계에 거부 큐 줄 수와 통째로 거부된 파일 수가 나온다.
- **PSP.** 지급 결과 통지는 기존 `/psp/webhook`(공유 비밀, 원문 보관 inbox, 멱등)이 그대로 맡는다.
- **미구현.** 파일 크기는 요청 본문 한도(약 1MiB)까지라 큰 리포트는 나눠 보낸다(큰 파일은 오브젝트 저장소 + 작업 큐로 옮긴다). 파트너 인증은 아직 개발용 신원이다(API 키·mTLS는 파트너를 붙일 때). DDEX ERN(메타데이터 수신)과 DSR 전체 규격, 외화 환산도 없다. 허브를 별도 서비스로 배포하는 것은 외부 유통을 시작할 때 한다(확장 경로).

## 권리 및 정산 코어 모듈

코어는 9개 모듈로 나뉘며 모듈 사이는 함수 인터페이스로만 호출한다. 다른 모듈의 테이블은 직접 쓰지 않는다. 현재 `rights-core`가 이 구조를 따른다.

| 모듈 | 책임 | 소유 데이터(주요) |
| --- | --- | --- |
| `registry` 권리 등록소 | 파티·작품·녹음·보이스·스템, 권리 주장·위임의 이중 시간축 버전, 분쟁, 이용허락 동의, 원천 문서(계약서 원문)와 근거 연결, 권리 요약 | `party`, `work`, `stem`, `right_claim`, `mandate`, `dispute`, `consent_agreement`, `source_document`, `record_evidence` |
| `policy` 정책 레지스트리 | MDRL 정책 작성·컴파일·시뮬레이션, 승인·활성화, 재고정 | `policy_version` |
| `issuance` 발행 | 팩 활성화 검사, 발행 시 스냅샷 동결 | `vocal_pack`, `rights_snapshot`, `issue_seal` |
| `revenue` 수익 수집 | 이벤트 멱등 수집, 순매출 확정, 무결성 플래그, 재생 기록과 감상 수익 풀 배정 | `revenue_event`, `play_event`, `traffic_pool` |
| `settlement` 정산 실행 | 배치 선정, 평가, 결과 봉인, 재계산 검증, 확정 | `settlement_run`, `allocation_line`, `unallocated_holding` |
| `ledger` 원장·지급 | 복식 원장 반영, 보류 해제, 지급 지시·PSP 연동, 명세 | 원장 테이블, `payout_instruction` |
| `disclosure` 공개 | Rights Manifest, 공개본, 플랫폼 서명, `/verify` | `manifest` |
| `engine-bridge` 엔진 경계 | 행→IR 변환, 봉인 저장, MDRL 호출 (MDRL을 import하는 유일한 모듈) | `sealed_document`, `attestation` |
| `platform` 공통 기반 | Outbox, 작업 큐, 감사 로그, 서명 API, 권한 | `outbox`, `audit_log`, `user_account` |

**동의 철회 후 노출 중지(구현 2026-10-15).** 동의를 철회하면 새 발행은 발행 게이트가 막고(`ISSUE_NOT_LICENSED`), 이미 발행된 조합은 노출 보류(`exposure_hold`)로 멈춘다.

- **언제 걸리나.** 철회 사건(outbox `consent_revoked`)을 처리할 때, 철회된 동의의 자산을 쓴 발행 조합마다 보류를 건다. 실연 동의는 그 보이스를 실연한 스템이 들어간 조합, 녹음 동의는 그 녹음의 스템이 들어간 조합, 작품 동의는 그 곡의 모든 조합이다.
- **무엇이 멈추나.** 팬 앱의 마스터 다운로드와 재생 기록이 410 `EXPOSURE_STOPPED`로 거부된다. 재생이 기록되지 않으므로 그 뒤 감상 매출도 생기지 않는다. 팬의 "내 조합"에는 노출 상태(STOPPED)가 보인다. 발행 봉인·이미 확정된 정산은 그대로이고, 미정산 매출의 보류·역분개 검토는 영향 분석을 보고 정산 담당이 정한다.
- **언제 풀리나.** 같은 파티가 같은 자산에 다시 동의하면 그 파티가 건 보류가 풀린다(재동의는 이전 철회를 대체한다). 운영자가 임의로 푸는 경로는 두지 않았다.
- **보이는 곳.** 운영·포털 `GET /exposure-holds`, 영향 분석의 "노출이 멈춘 조합", ⑧ 분쟁·철회 단계 신호 "동의 철회로 노출이 멈춘 조합".

**멤버별 기여분(구현 2026-10-15).** 소속사에 실연 권리를 위임한 멤버는 직접 받는 금액이 없어 명세가 비어 있다. 실연자 앱 "수익" 탭은 위임 전 내 몫을 참고값으로 보여 준다(`GET /performer/contributions`).

- **계산.** 확정된 정산 run마다 그 run의 매출을 같은 발행 봉인으로 다시 평가하되, 정책에서 위임 라우팅(`via mandate`)만 뺀다(엔진 시뮬레이션). 봉인·원장에는 쓰지 않는다.
- **금액 기준.** 정산 때의 순액에서 확정 뒤 환불(역분개)을 뺀다. 이상거래 보류가 풀리지 않은 매출은 권리자 풀이 배분되지 않으므로 기여분도 0이고, 건수로 따로 보여 준다.
- **검증.** 위임한 멤버가 한 명이면 그 멤버의 기여분 합 = 소속사가 실연 버킷에서 받은 금액(역분개 포함)이다. 위임이 없는 멤버는 기여분 = 실제로 받은 실연 몫이다.

**감상 매출(구현 2026-10-15).** 구매는 조합 한 건에 매출 한 건이 바로 붙지만, 구독·광고 수익은 기간 단위로 들어온다. 그래서 두 단계로 나눈다.

1. **재생 기록.** 팬 앱이 재생을 보고한다(`POST /fan/plays`, `play_event`). 앱이 만든 재생 id로 멱등이고, 재생 시각은 코어 시계로 적는다. 30초 이상이면 유효 재생이다. 같은 사용자가 같은 조합을 24시간 안에 10번 넘게 유효 재생하면 그 뒤 재생은 FLAGGED로 남기고 배정에서 뺀다.
2. **풀 배정.** 정산 담당이 기간 수익 풀(`traffic_pool`, 구독 또는 광고, 기간, 금액)을 등록하고 배정한다. 기간의 유효·CLEAR 재생을 조합별로 세어 최대잉여 방식으로 나눈다. 몫의 합은 풀 금액과 같고, 남는 원은 소수부가 큰 조합부터(같으면 조합 id 순) 준다. 조합마다 `TRAFFIC` 매출 이벤트가 하나씩 생긴다. 이벤트 시각은 기간의 마지막 밀리초라서 같은 기간 정산 배치에 들어간다.

- **그 뒤는 구매와 같다.** 정산 배치 → 엔진 평가(봉인 정책) → 독립 재계산 검증 → 확정 → 원장 순서다.
- **정책이 감상 매출을 받아야 한다.** 조합의 봉인 정책 범위(`scope.events`)에 `TRAFFIC`이 없으면 그 조합의 재생은 배정에서 뺀다(`POLICY_NO_TRAFFIC`). 그대로 넣으면 엔진이 run을 거부하고 조합이 격리된다. 뺀 재생 수는 풀에 사유별로 남는다.
- **`TRAFFIC`은 풀 배정과 연동 허브에서만 생긴다.** 둘 다 정책이 감상 매출을 받는지 확인한다. 매출 수집 API로 직접 올리면 422 `TRAFFIC_VIA_POOL`이다. 환불 대상도 될 수 없다.
- **배정은 한 번이다.** 유효 재생이 없으면 풀은 NO_PLAYS로 닫히고 금액은 배정되지 않는다.
- **⑧ 수익 단계 신호.** 최근 7일 유효 재생, 과다 반복 재생, 기간이 끝났는데 배정 안 된 풀, 재생이 없어 배정 못 한 풀.
- **미구현.** 풀 금액 정정(재배정), 구독자 재생만 세는 구독 풀 구분. 외부 유통사의 감상 매출은 재생 수가 아니라 유통사가 정한 조합별 금액으로 연동 허브가 받는다(아래 "연동 허브").

## 사용자 업무 시스템 분리

업무 시스템은 사용자 유형이 아니라 권한을 기준으로 나누고, 신뢰 경계에 따라 앱 4개(팬 앱, 실연자 앱, 권리자 포털, 운영 백오피스)로 배포한다. 플랫폼은 권리를 결정하지 않지만, 권리 생성부터 정산까지 전 구간을 조회하고 이슈에 개입한다.

![사용자 업무 시스템 · 배포 앱 4개, 업무 시스템 8개](images/업무시스템_결정권한.png)

**실연자 앱(구현 2026-10-15, `performer-app`).** 모바일 우선 PWA다. 홈 화면에 설치할 수 있고(웹 매니페스트), 서비스 워커가 웹 푸시를 받는다. 실연자 채널(`/performer`)만 호출한다.

| 탭·화면 | 하는 일 | 코어 |
| --- | --- | --- |
| 본인 인증 | 일회용 코드로 본인 인증. 끝내기 전에는 동의 서명 불가(`IDENTITY_REQUIRED`) | `identity_challenge`, `user_account.identity_verified_at` |
| 동의 | 내 보이스별 동의 상태, 동의(팬앱 범위·1년)·철회(사유 필수). 철회하면 계약서 동의까지 새 발행을 막고, 다시 동의하면 풀린다 | `consent_agreement` |
| 사용 | 내 스템이 쓰인 발행 조합(파트·길이) | `snapshot_stem_assignment` |
| 수익 | 올해 명세(정산·역분개·보류 해제·실지급·잔액). 소속사 위임이면 실연 몫은 소속사 명세에 있고, 대신 위임 전 내 기여분(참고값)을 조합별로 보여 준다 | 원장, 엔진 시뮬레이션 |
| 이의제기 | 나와 관련된 권리 주장(보이스 소유·스템 실연)에 이의 → 분쟁(곡 소유 테넌트 소유, 연 사람 기록), 팩 일시정지 | `dispute.opened_by` |
| 알림 | 사용·동의·지급·이의제기 알림함, 웹 푸시(VAPID) 구독 | `notification`, `push_subscription` |

본인 인증 공급자는 인터페이스로 분리했다. 개발 서버는 코드를 화면에 보여 주는 개발용 공급자를 쓰고, 운영 공급자(휴대폰·PASS)는 아직 없다(미설정이면 503). 로그인도 아직 개발용 계정 id다. 네이티브 앱(스토어 배포)은 이 PWA로 흐름을 검증한 뒤 정한다.

**팬 앱 조합 판정과 캐시(구현 2026-10-15).** 팬은 슬롯마다 스템을 바꿔 가며 여러 배치를 시험한다. 그때마다 "이 배치를 지금 발행할 수 있는가"를 묻는 것이 조합 판정(`POST /fan/combinations/check`)이다.

- **판정 = 실제 발행을 되돌린 것.** 판정은 실제 발행 함수를 SAVEPOINT 안에서 돌리고 되돌린다. 팩 상태·분쟁·스템 오디오(READY)·이용허락·정산 사전 검사가 발행과 똑같이 적용되고, 스냅샷·봉인 행·알림은 남지 않는다. 거부도 판정 결과다(200, `issuable: false`, 발행과 같은 코드와 진단).
- **캐시 키.** 팩, 활성 정책 digest, 배치(슬롯 순 정렬), 멤버 비율, 이용 범위를 JCS로 정규화해 해시한다. 정책을 새로 활성화하면 키가 달라져 옛 판정은 쓰이지 않는다. 항목은 5분 뒤 만료된다(동의 유효기간처럼 시각에 따라 바뀌는 판정 때문).
- **선택 무효화.** 판정이 의존하는 것이 바뀌면 그 판정만 지운다. 바꾼 쪽 트랜잭션에서 같이 지우므로 커밋·롤백이 함께 간다.

| 바뀐 것 | 지우는 판정 |
| --- | --- |
| 실연 동의 서명·철회 | 그 보이스를 쓴 판정 |
| 스템 오디오 올리기·검사·검토 | 그 스템을 쓴 판정 |
| 녹음·작품 동의, 권리 주장·위임 기록(분쟁 개시·종결 포함), 팩 활성화·일시정지 | 그 곡의 판정 전부 |

- **경합.** 무효화할 때마다 곡의 세대 번호(`decision_epoch`)를 올린다. 판정을 계산하는 동안 무효화가 있었으면(세대가 바뀜) 저장하지 않는다. 저장할 때는 세대 행을 공유 잠금으로 잡으므로, 저장과 겹친 무효화는 저장이 커밋된 뒤에 지운다.
- **캐시는 안내용이다.** 실제 발행(`POST /fan/combinations`)은 캐시를 보지 않고 게이트를 다시 돈다. 캐시가 틀려도 잘못된 발행은 생기지 않는다.
- **그 밖의 팬 표면.** 팩 상세(`GET /fan/packs/:id`, 스템별 사용 가능 여부), 내 조합(`GET /fan/combinations`, 렌더 상태). ⑧ 발행 단계에 캐시 항목 수·적중 신호가 있다.
- **남는 것.** 판정의 봉인 원문(조합 지분·멤버 IR)은 content-addressed blob으로 먼저 써지고 DB 행만 되돌려진다. 이 blob은 15번(롤백으로 남은 blob 정리)이 치운다. 판정 서비스를 코어 밖으로 떼어 내는 것은 팬 트래픽이 코어 응답에 영향을 줄 때 한다(확장 경로).

**API 채널(구현 2026-10-15).** 코어 API는 앱마다 다른 경로 앞부분(채널) 아래에 열리고, 채널마다 들어올 수 있는 신원이 정해져 있다. 같은 처리기를 두 채널에 올려도 채널 정책이 먼저 신원을 거른다(403 `CHANNEL_FORBIDDEN`). 역할 검사와 RLS는 그 뒤에 따로 적용된다.

| 채널 | 앱 | 들어올 수 있는 신원 | 주요 표면 |
| --- | --- | --- | --- |
| `/ops` | 운영 백오피스 | 플랫폼 운영 테넌트 사용자 | 전 모듈(등록·정책·발행·매출·정산·원장·지급·감사·테넌트) |
| `/portal` | 권리자 포털 | 권리자 테넌트(레이블·기획사·출판사·신탁단체) 사용자, 플랫폼 운영 | 등록·정책·팩·동의, 자기 테넌트 파티와 명세 |
| `/performer` | 실연자 앱 | PERFORMER 역할의 본인 계정 | 본인 동의 서명·철회, 내 스템 사용 이력, 내 명세 |
| `/fan` | 팬 앱 | 팬 파티에 연결된 개인 계정 | 활성 팩 카탈로그·상세, 조합 판정(캐시), 조합 발행(팬 대신 발행, 감사 행위자는 팬), 내 조합, 미리듣기·마스터, 재생 보고 |
| `/partner` | 파트너 연동 | B2B 파트너 테넌트 사용자 | 리포트 파일 전송(유통사 CSV·DDEX DSR), 내 파일의 줄별 결과(거부 사유), 내 자산 대응 |

실연자 앱은 모바일 전용 앱으로 따로 둔다. 보컬리스트는 동의 서명·철회와 수익 확인처럼 짧고 잦은 본인 업무를 휴대폰에서 하고, 본인 인증·푸시 알림이 필요하며, 테넌트 권한이 아니라 본인 데이터만 본다. 권리자 포털은 권리자·파트너용 웹으로 남는다. 네 앱은 같은 코어를 쓰지만 API 표면과 인증이 다르고, 운영 백오피스는 SSO와 접근 IP 제한 뒤에만 둔다.

## 업무 시스템별 결정 주체와 직무 분리

권리에 관한 결정(①~③)은 권리자만, 동의(④)는 실연자 본인만 하고, 플랫폼(⑤~⑧)은 관제·검증·집행만 한다. 플랫폼 화면에는 권리 승인 버튼을 두지 않는다.

| 업무 시스템 | 배포 앱 | 결정 주체 | 핵심 업무 | 반드시 분리할 직무 |
| --- | --- | --- | --- | --- |
| ① 권리 등록·카탈로그 | 권리자 포털 | 권리자 | 작품·녹음·스템·슬롯, 권리 주장·위임, L0 원본 권리 이미지 | — |
| ② 정책·상품(팩) | 권리자 포털 | 권리자 | MDRL 정책 작성·시뮬레이션, 팩 차분, 승인·활성화 | 편집자 ≠ 승인자 ≠ 활성화자 |
| ③ 발행·심사 | 권리자 포털 | 권리자 | 72시간 발행 승인 큐, 권리 검토 큐(침해·브랜드 훼손) | — |
| ④ 동의·실연자 | 실연자 앱(모바일) | 실연자 본인 | 동의 서명·철회, 내 스템 사용 이력, 수익 조회, 이의제기 | — |
| ⑧ 권리 파이프라인 관제 | 운영 백오피스(홈) | 플랫폼 | 권리 생성부터 지급까지 단계별 관제, 한 건 추적, 영향 분석, 이슈 배정 | 관제 담당자 ≠ 감사 담당자 |
| ⑤ 무결성·신뢰안전 | 운영 백오피스 | 플랫폼 | QC, 검증 리포트(PASS/FAIL만), 플랫폼 정책 검토, 킬 스위치, 분쟁 | 조사자 ≠ 판정자 |
| ⑥ 정산·재무 | 운영 백오피스 | 플랫폼 | 배치 실행·확정, 원장, 보류 해소, 지급, 세무 | 실행자 ≠ 확정자, 계좌 변경자 ≠ 승인자 |
| ⑦ 관리·감사 | 운영 백오피스 | 플랫폼 | 테넌트, 사용자·권한, 위임 대행 업무함, 감사로그 | — |

테넌트가 명시적으로 위임한 업무만 ⑦의 대행 업무함에서 처리하고, 처리 내역은 `acting_on_behalf_of`로 감사로그에 남긴다. 직무 분리는 서비스 검사와 DB 제약으로 이중 강제한다.

## 권한의 세 가지 구분

플랫폼은 권리를 결정하지 않지만 전 구간을 조회하고 개입한다. 개입은 흐름을 멈추고, 돈을 묶고, 다시 돌리고, 권리자에게 넘기는 것까지다.

| 권한 | 권리자 | 플랫폼(운영 백오피스) |
| --- | --- | --- |
| 결정: 권리 내용 확정·승인·활성화 | 한다 | 하지 않는다(위임받은 업무만 대행 업무함에서) |
| 조회: 권리 생성부터 정산·지급까지 | 자기 테넌트만 | 전 테넌트, 단계별 통제 적용 |
| 개입: 멈춤·보류·재처리·라우팅 | 자기 범위 안에서 | 한다. 권리 내용은 바꾸지 않는다 |

## ⑧ 권리 파이프라인 관제

⑧은 운영 백오피스의 홈이다. 파이프라인을 단계별로 보고, 이슈를 ⑤ 무결성·신뢰안전과 ⑥ 정산·재무 큐로 넘기거나 권리자에게 라우팅한다.

| 단계 | 관제할 신호 | 플랫폼의 1차 대응 | 최종 결정 |
| --- | --- | --- | --- |
| 권리 등록(L0·권리 주장·위임) | 증빙 미확인, 지분 합계 오류, 위임 만료 임박 | 권리자에게 보완 요청 | 권리자 |
| 정책(컴파일·승인·활성화) | 재고정 대기 정책, `FACTS_CLAIMANT_DRIFT` 경보 | 활성화 차단 상태 표시, 재고정 요청 | 권리자 |
| 팩 활성화 | 계승 위반, 동의 커버리지 부족, stale 팩 | 검증 리포트 FAIL, 판매 노출 중지 | 권리자 |
| 조합 발행(게이트·봉인) | 게이트 거부율, 72시간 승인 만료 | 거부 사유 집계, 기한 임박 알림 | 권리자 |
| 수익 유입·대사 | 미매칭·중복·충돌 이벤트, 원천 보고와의 차이 | 거부 큐 처리, 재수집 | 플랫폼 |
| 정산 실행·검증 | 재계산 불일치(목표 0건), 사유별 보류 금액 | run VOID, 재실행 | 플랫폼(실행자 ≠ 확정자) |
| 원장·지급 | 지급 실패, 계좌 냉각, 중복 웹훅 | 지급 보류, 재시도 | 플랫폼 |
| 분쟁·철회(전 구간) | 분쟁으로 일시정지된 팩 수, 철회 전파 지연 | 영향 범위 산출, 자동 보류, 킬 스위치(법규·사기 사유) | 권리자 판정, 플랫폼 집행 |

신호 대부분은 시스템통합 설계 6.6절(관측)과 IA의 1.2 실시간 모니터링·4.0 권리 구조 통합 인스펙터에 이미 정의돼 있다. ⑧은 화면별로 흩어진 이 신호를 파이프라인 하나로 묶는다.

**구현(2026-10-15).** 운영 백오피스의 첫 화면(`/`)이 ⑧이다. 신호는 `/ops/pipeline/signals`, 한 건 추적은 `/ops/trace?vc=|event=|party=`, 영향 분석은 `/ops/impact?consent=|dispute=|claim=`이 계산한다. 위 표의 신호 중 증빙 미확인 주장, 분쟁, 위임 만료 임박, 승인 대기·재고정 필요 정책, 팩 상태, 게이트 거부율과 사유, 이상거래·미확정 매출, 재계산 실패·격리·사유별 보류 금액, 지급 실패·결과 불명·지급 보류, 동의 철회와 그 영향 조합을 구현했다. 원천 보고 대사, 72시간 승인 만료, 철회 전파 지연은 해당 기능이 생길 때 붙인다.

n차 저작권이라서 두 기능이 필수다.

- **한 건 추적**: 조합 ID·매출 이벤트 ID·파티 중 하나로 시작해 원곡 → 녹음 → 스템 → 조합 → (2차 조합) → 매출 → 정산 라인 → 지급을 한 화면에 잇는다. 단계마다 봉인 digest·정책 버전·기준 시점을 표시해 금액의 근거를 설명한다.
- **영향 분석**: 권리 주장 변경·동의 철회·분쟁이 생기면 하위 파생 조합, 미정산 매출, 확정된 정산 라인까지 영향 범위를 보여주고, 보류할 것과 역분개할 것을 가른다. 기획서 13.3절의 역방향 의존성 인덱스가 기반이다.

전 테넌트 조회는 테넌트 격리와 충돌하지 않도록 단계별로 연다.

| 조회 단계 | 범위 | 조건 |
| --- | --- | --- |
| 기본 조회 | 상태·메타데이터·금액 합계·digest, 개인정보 마스킹 | 관제 역할이면 항상 |
| 상세 조회(break-glass) | 계약서 원문, 개인별 지분, 계좌 정보 | 이슈 케이스에 연결하고 사유를 기록한 경우만 |
| 감사 | 모든 조회·개입 기록 | 감사로그에 남기고, 관제 담당자와 감사 담당자를 분리 |

## 확장 경로

분리는 미리 하지 않고, 아래 신호가 실측될 때 한 단계씩 진행한다.

| 신호 | 조치 | 유지할 원칙 |
| --- | --- | --- |
| 정산 이벤트가 하루 1,000만 건 규모로 실측됨 | 정산 실행을 별도 워커 풀로 분리, 정산 그룹 단위 집계 도입 | DB 공유, run 단위 트랜잭션 |
| 권리 그래프 탐색이 병목으로 실측됨 | 그래프 읽기 모델(또는 그래프 DB) 도입 | 원본은 PostgreSQL, 읽기 모델은 재생성 가능 |
| 외부 유통사·DSP 연동 시작(로드맵 3단계) | 연동 허브를 독립 배포 | 코어에는 정규화된 이벤트만 전달 |
| 팬 조합 트래픽이 코어 응답에 영향을 줌 | 조합 빌더·판정 캐시를 독립 배포 | 발행 봉인은 코어에서만 만든다 |
| 파트너가 정산 결과를 직접 검증하려 함 | MDRL tarball과 `/verify` 공개 | 엔진은 라이브러리 하나, 같은 버전이면 같은 digest |

성능 목표(권리 게이트 캐시 적중 p95 100ms, 예상 배분 반영 p95 5초)는 기획서의 제안값이며 아직 실측되지 않았다.

## 현재 구현과의 차이와 다음 작업

코어(`rights-core` + `mdrl`)는 이 구조를 따르고 테스트(엔진 307, 오디오 6, 코어 DB 395, 연동 허브 6, 백오피스 80, 실연자 앱 4, E2E 21+1)를 통과한다. 남은 작업 15개를 앞 작업이 뒤 작업의 전제가 되도록 네 단계로 묶고, 선행 작업이 없는 운영 준비 작업을 따로 두었다. "선행"은 먼저 끝나야 하는 작업 번호다.
