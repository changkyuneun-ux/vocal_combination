# dobedupop MVP 진행계획 — Dynamite 2차 이용 데모

- 작성일: 2026-10-16
- 근거: [시스템 아키텍처 및 업무 분리안](시스템_아키텍처_및_업무분리안_20261012.md), [예시: Dynamite 2차 이용](예시_Dynamite_2차이용_권리생성에서_지급까지_20261012.md), [원천 문서 관리 설계](원천문서_관리와_권리·정책_입력·조회_설계_20261015.md)

## 목표

MVP는 상용 시스템의 출발점이다. 권리자 포털·실연자 앱·운영 백오피스를 서브도메인으로 나눠 배포하고, BTS "Dynamite" 2차 이용과 비슷한 가상 데이터로 권리 등록부터 지급까지 전 흐름을 한 번에 시연한다.

상용 개발이 이 MVP를 그대로 이어받으므로 원칙은 하나다. **데모를 위한 별도 코드 경로를 만들지 않는다.** 화면·API·정책·DB 제약은 운영과 같은 것을 쓰고, 데모 전용인 것은 세 가지뿐이다.

- 가상 데이터(Dynamite 시드)
- 인터페이스 뒤의 가상 공급자(PSP·본인 인증·전자서명)
- 데모 진행판

## 범위

| 구분 | 내용 |
| --- | --- |
| 포함 | 권리자 포털(① 권리 등록, ② 정책·팩, ③ 발행·심사, 원천 문서·정합성 점검·표준 계약), 실연자 앱(④ 동의·실연자), 운영 백오피스(⑤ 무결성, ⑥ 정산·재무, ⑦ 관리·감사, ⑧ 관제), 권리 및 정산 코어, 오디오 처리 서비스, 연동 허브, 게이트웨이 |
| 제외 | 팬 앱 화면, 공개 `/verify`, 파트너 채널의 외부 공개 |
| 가상으로 대체 | 팬 활동(조합 발행·구매·재생)은 가상 팬 생성기가 내부망에서 코어 팬 채널(`/fan`)을 호출한다. 유통사 리포트는 가상 CSV 파일로 연동 허브에 넣는다. PSP·본인 인증·전자서명은 지금처럼 인터페이스 뒤 가상 공급자로 둔다 |

팬 앱을 빼도 팬 채널 API는 코어에 그대로 둔다. 조합 판정·발행 게이트·이용허락 판정이 그 경로에 있어서, 빼면 정책이 시연되지 않는다. 게이트웨이는 `/fan`을 외부에 열지 않는다.

## 서브도메인 구성(가상)

| 주소 | 앱 | 게이트웨이가 허용하는 API | 들어오는 사람 |
| --- | --- | --- | --- |
| `portal.dobedupop.localhost` | 권리자 포털 | `/api/portal` | 레이블·기획사·출판사·작가 테넌트 사용자 |
| `artist.dobedupop.localhost` | 실연자 앱(모바일 PWA) | `/api/performer` | 본인 인증을 마친 실연자 |
| `ops.dobedupop.localhost` | 운영 백오피스 | `/api/ops` | 플랫폼 운영 사용자(접근 IP 제한) |
| `demo.dobedupop.localhost` | 데모 진행판 | `/api/demo` | 시연자(데모 환경에서만 배포) |

- **로컬 주소:** `*.localhost`는 브라우저가 hosts 파일 없이 내 컴퓨터로 연결한다. 데모 서버나 상용으로 옮길 때는 환경 설정의 기본 도메인만 바꾼다.
- **같은 출처의 API:** 앱마다 자기 서브도메인의 `/api` 아래로 코어를 부른다. 쿠키가 서브도메인별로 갈리고 CORS 설정이 필요 없다.
- **채널 이중 차단:** 게이트웨이가 호스트별로 허용 채널을 거르고, 코어의 채널 정책(`CHANNEL_FORBIDDEN`)이 한 번 더 거른다. 예를 들어 포털 주소로는 `/api/ops`에 닿지 않는다.

## 설계 구조·정책 반영

이미 구현된 것은 MVP에서 그대로 쓰고, 배포 구조에서 새로 갖춰야 하는 것만 단계 작업으로 둔다.

| 설계 원칙 | MVP 반영 | 지금 상태 |
| --- | --- | --- |
| 코어는 한 프로세스·한 DB, 판정·봉인·정산·원장을 한 트랜잭션 | 코어 이미지 하나를 API·워커·검증 워커 역할로 나눠 실행(같은 DB) | 구현됨. 단, 워커가 API와 같은 프로세스 → M2 |
| 독립 검증 워커는 다른 신원 | 검증 워커를 별도 컨테이너·별도 서비스 계정으로 실행 | 신원 분리는 구현, 프로세스 분리는 M2 |
| MDRL은 라이브러리, `engine-bridge`만 import | 그대로 | 구현됨 |
| IR 봉인·digest, 수정 불가 | 봉인 원문을 오브젝트 저장소로(다음 작업 15번) | 로컬 파일 → M2 |
| 오디오 처리·연동 허브 분리 | 각각 별도 컨테이너 | 패키지 분리만 됨 → M2 |
| 멀티테넌시 RLS, 조회 통제(열람 기록·마스킹·break-glass) | 그대로. 세션의 사용자·테넌트로 범위 설정 | 구현됨. 신원은 개발용 `x-actor` 헤더 → M3 |
| 채널별 표면과 인증 | 서브도메인 = 채널, 앱별 로그인 | 채널은 구현, 인증은 M3 |
| 직무 분리(편집 ≠ 승인 ≠ 활성화, 실행 ≠ 확정, 요청 ≠ 승인, 법무 작성 ≠ 승인) | 데모 페르소나를 역할별로 따로 둔다 | 구현됨 |
| ⑧ 관제·한 건 추적·영향 분석 | 운영 백오피스 홈 | 구현됨 |
| 원천 문서·정합성 점검·표준 계약(S1~S4) | 가상 계약서 원문을 시드에 넣는다 | 구현됨. 원문 저장소는 로컬 파일 → M2 |
| 가상 공급자는 운영에서 거부 | 환경 구분 `demo`·`production`. production은 가상 공급자로 시작하지 않는다 | 공급자별 503 거부는 구현, 환경 구분은 M2 |

## 디렉터리 구조

MVP 홈은 저장소 안에 새로 만들되, 안쪽은 영문 경로의 독립 저장소 형태로 둔다. 나중에 상용 저장소로 떼어 낼 때(`git subtree split`) 그대로 옮길 수 있다.

```
06_MVP/dobedupop/
├── package.json              워크스페이스(아래 패키지 전부)
├── apps/
│   ├── backoffice/           권리자 포털·운영 백오피스(한 코드베이스, 두 빌드)
│   ├── performer/            실연자 앱
│   └── demo-console/         데모 진행판(데모 환경에서만 빌드·배포)
├── services/
│   ├── rights-core/          권리 및 정산 코어(API·워커·검증 워커 역할)
│   ├── audio-service/        오디오 처리 서비스
│   └── integration-hub/      연동 허브
├── packages/
│   └── mdrl/                 MDRL 엔진 라이브러리
├── demo/
│   └── dynamite/             가상 데이터 정의·단계별 시나리오·가상 팬 생성기·가상 계약서 원문
├── deploy/
│   ├── gateway/              서브도메인 라우팅·채널 제한·보안 헤더
│   ├── docker/               서비스·앱별 Dockerfile
│   ├── compose/              compose.yml(공통), compose.demo.yml(데모 추가분)
│   └── env/                  demo.env.example, production.env.example
└── docs/                     데모 가이드, 운영 런북, 요건 추적표, 결정 기록
```

`04_구현_소스코드`의 패키지는 복사하지 않고 옮긴다(MD2). 복사하면 두 벌의 코드에서 정책이 갈라진다.

## 데모 시나리오

Dynamite 예시 문서의 12단계를 앱별 화면 흐름으로 다시 묶었다. 데모 진행판은 각 단계를 실행하거나 건너뛰게 하고, 다음에 열 앱과 페르소나를 링크로 보여 준다.

| 순서 | 무엇을 보여 주나 | 앱 | 페르소나 |
| --- | --- | --- | --- |
| 1 | 곡·녹음·스템·슬롯 등록, 녹음 계약서 원문 올리기, 권리 요약 | 포털 | 레이블 권리 편집자 |
| 2 | 작가 지분 주장 → 상대 확인 요청, 작품 이용허락 표준 계약(가상 공급자 서명) | 포털 | 레이블·출판사 |
| 3 | 멤버 수익 수령 위임계약 서명, 본인 인증, 팬앱 이용 동의 | 실연자 앱 | 멤버 7명 |
| 4 | 정합성 점검: 빠진 근거가 활성화를 막고, 고치면 풀린다 | 포털·운영 | 레이블, 컴플라이언스 |
| 5 | 분배 규칙 폼 → 예시 계산 → 승인 → 활성화, 팩 활성화 | 포털 | 편집자·승인자·활성화 담당(세 사람) |
| 6 | 가상 팬의 조합 발행과 구매. 철회한 멤버가 부른 조합은 발행 거부 | 진행판 → 운영 | 가상 팬 생성기 |
| 7 | 매출 수집·정산 실행 → 독립 재계산 → 확정 | 운영 | 정산 실행자 ≠ 확정자 |
| 8 | 원장·지급(가상 PSP), 명세 | 운영·포털·실연자 앱 | 정산 담당, 권리자, 멤버 |
| 9 | 유통사 리포트(가상 CSV)와 감상 수익 풀을 재생 비중으로 배정 | 운영 | 운영 |
| 10 | 동의 철회·이의제기 → 노출 중지, 영향 분석, 환불 역분개 | 실연자 앱 → 운영 | 멤버, 운영 |
| 11 | ⑧ 관제에서 조합 하나를 원곡부터 지급까지 한 건 추적 | 운영 | 관제 담당 |

## 페르소나 E2E 점검(2026-10-16)

"빅히트 테넌트·권리자·실연자·운영자가 각자 로그인해 Dynamite 권리와 정산을 끝까지 시연할 수 있는가"를 코드로 확인했다. 기존 Dynamite 시나리오는 플랫폼 계정이 서비스 함수를 직접 부르는 스크립트라(빅히트 테넌트 없음, 권리 기록을 바로 VERIFIED로 쓰고 동의를 플랫폼이 옮겨 적음) 이 질문에 답하지 못했다. 그래서 모든 단계를 페르소나의 채널 API로 부르는 시나리오(`services/rights-core/src/scenario/dynamite-personas.ts`)를 만들어 돌렸다. 이 시나리오가 M4 데모 시드의 바탕이 된다.

| 단계 | 페르소나(채널) | 결과 |
| --- | --- | --- |
| 0 온보딩 | 운영 SPACE_OPS: 빅히트 뮤직 테넌트 등록. 플랫폼 온보딩 담당(플랫폼 RIGHTS_EDITOR): 멤버·작가·팬 파티 | 통과 |
| 1 권리 등록 | 빅히트 권리 편집자(포털): 레이블·소속사 파티, 곡·녹음·슬롯 8·스템 50·보이스 7, 녹음·퍼블리싱 계약서 원문 | 통과 |
| 2 권리 주장 | 빅히트: 녹음 권리(자기 파티라 바로 확정), 작가 지분(ASSERTED), 보이스 소유·스템 실연 56건(ASSERTED → 멤버 확인 요청) | 통과 |
| 3 멤버 | 멤버 7명(실연자 앱): 본인 인증 → 확인 요청 확인 → 이용 동의(동의서 원문 생성) | 통과 |
| 4 표준 계약 | 빅히트: 플랫폼 계약·녹음 이용허락(레이블 서명), 멤버별 수령 위임(멤버·소속사 서명). 플랫폼: 작품 이용허락(작가 = 공급자 서명) | 통과 |
| 5 운영 | 지급 정보(계좌 담당), 작가 지분 기한 뒤 원문 대조 확인 | 통과 |
| 6 정책·팩 | 빅히트 정책 편집 ≠ 승인 ≠ 활성화(세 사람), 정합성 점검 차단 0건, 팩 활성화 | 통과(아래 수정 1 뒤) |
| 7 발행 | 가상 팬 4명(팬 채널): 조합 4개 발행, 솔로 조합 거부(`ISSUE_NOT_SETTLEABLE`) | 통과 |
| 8 정산 | 수집 시스템 매출 → 운영 정산 실행 → 독립 재계산(VERIFIED) → 다른 담당 확정 → 환불 역분개 | 통과 |
| 9 지급·명세 | 운영 지급 실행, 빅히트 포털 명세(레이블·소속사), 멤버 기여분(실연자 앱) | 통과 |
| 격리 | 빅히트는 작가 명세를 못 봄(404), 멤버는 포털 불가(403), 빅히트는 운영 채널 불가(403) | 통과 |

점검에서 나온 것과 처리:

- [x] **정합성 규칙 오탐 수정**: 실연 몫 전부를 확정 위임(100%)한 멤버에게도 "지급 정보 없음"을 냈고, 14일 뒤 차단으로 올라 활성화를 막았다. 멤버는 직접 받지 않으므로 대상에서 뺐다
- [x] **역할 정리**: 플랫폼의 파티 등록(멤버·작가·팬)은 운영(SPACE_OPS)이 아니라 플랫폼 온보딩 담당(플랫폼 RIGHTS_EDITOR)이 한다. 플랫폼 밖 작가와의 작품 이용허락은 이용자인 플랫폼이 작성·반영한다(빅히트는 작가 파티를 볼 수 없다)
- [x] **사용자 관리 API**: 계정 발급·역할 부여 API가 없다(지금은 개발 시드). → M3 완료(2026-10-16)
- [x] **지급 완료 통지**: 지급 지시는 PENDING에서 PSP 통지로 PAID가 된다(M4: 데모 스택에서 가상 PSP 조회로 PAID 확인). 데모 환경에서 가상 PSP 통지를 보내는 길이 필요하다. 역할을 나누면 개발용 PSP 상태가 프로세스마다 따로인 문제도 함께 푼다. → M4
- [ ] **화면 동선**: API로는 끝까지 가지만, 테넌트 사용자가 포털 화면만으로 각 단계를 할 수 있는지(메뉴·폼)는 화면을 따라가며 확인해야 한다. → M5
