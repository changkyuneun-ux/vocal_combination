# 보컬조합 라이선스·정산·모니터링·백오피스 개념 설계

상태: 개념 설계 (구현 전)
기준 자료: `01_기획문서` 목차, `backend-rights-screen.html`, `settlement-admin-console.html`, `vocal-customizing-service.html`

## 1. 사업 이해

보컬조합은 **라이선스가 허용한 보컬 스템**을 팬이 STEM/CUBE로 조합하고, 정책 검증을 통과한 결과를 **고유 ID의 디지털 자산**으로 발행하는 플랫폼이다.

- 팬은 공동저작권자가 아니다. 참여 보상(포인트, 크레딧, 제한적 수익)만 갖는다.
- 발행 시점에 원천 IP, 허용/불가 범위, 배분 룰 버전을 **권리 스냅샷**으로 고정한다.
- 매출 이벤트는 1차 소장 구매, 2차 재판매, 이벤트 보상, 환불로 나뉜다.
- 외부 상업 유통·무단 다운로드는 기본 금지, 팬클럽 공유는 조건부이다.

## 2. 권장 아키텍처

**권리 코어 + 이해관계자 포털.** 라이선스·정책·이벤트 원장을 하나로 두고 화면만 역할별로 나눈다.

| 접근 | 채택 | 이유 |
| --- | --- | --- |
| A. 단일 SPACE 콘솔 | 초기만 | 기존 목업과 같으나 권리자 감사·셀프서비스가 약함 |
| B. 권리 코어 + 포털 | **권장** | 정산 근거 일원, 최소 권한 |
| C. 이해관계자별 별도 시스템 | 비권장 | 스냅샷·배분 불일치 |

코어 계층: 권리 등록소 → 정책 엔진 → 발행 런타임(스냅샷) → 이벤트 원장 → 정산 엔진 → 포털·감사.

## 3. 라이선스 관리

권리 **주체(Party)** 와 **그랜트(LicenseGrant)** 를 분리한다. 목업의 “권리자 70%”는 풀이지 단일 계좌가 아니다.

주체: 레이블/소속사, 아티스트/멤버, 작곡·작사·출판, 신탁단체, 플랫폼, 팬(보상권만).

자산 계층: 작품 → 마스터/보컬팩 → 스템/파트 → 멤버 음성 → 이용 그랜트.

그랜트 차원: 허용 행위, 지역, 기간, 파트, 조합 정책(1인 90% 미만 등), 정산 템플릿.

상태: 초안 → 활성 → 제한 → 만료/철회, 별도 분쟁 홀드.

**조합 검증은 UX가 아니라 그랜트 + 발행규칙 + 조합제약 + 유일키 + 스탬프 발행가능 평가**이다. 공식 발행 전에 검증 런과 승인을 남기고, 개인 소장·플랫폼 배포·한정 이용 조항이 찍힌 권리 스탬프가 있어야 `ISSUED`가 된다. 룰 변경은 이후 발행분에만 적용한다.

## 4. 정산 룰

정산은 **현재 계약이 아니라 VC ID 스냅샷**으로 한다. 계약 변경은 보정 이벤트로만 반영한다.

파이프라인: 총매출 → PG·환불·부가세 차감 → 순매출 → 3풀(권리자/플랫폼/팬) → **AllocationPolicy로 권리자 풀 내부 안분** → 최소지급·홀드·이월 → 지급.

### 4.1 안분 정책은 선택이거나 믹스다

권리자 70%를 한 계좌에 넣지 않는다. IP·이벤트유형(1차/2차)마다 `AllocationPolicy`를 두고, 아래 베이스를 **단독 선택**하거나 **믹스**한다. 레시피 전체는 발행 스냅샷에 붙는다.

| 베이스 | 입력 | 산출 |
| --- | --- | --- |
| `STEM_TIME` | 스템별 재생(또는 배정) 초, 스템→파티 맵, 잠금 스템 포함 여부 | 실연자 사용 비중 |
| `MEMBER_PCT` | 빌더 멤버 %(발행 검증과 동일, 합 100%) | 실연자 구성 비중 |
| `CONTRACT` | 파티별 고정 지분 (합 100%) | 레이블·멤버·신탁 등 전 청구자 |

사용량 키는 실연자 벡터만 만든다. 레이블·신탁이 있는 IP에 사용량 단독을 저장하면 “청구 주체 미커버”로 거부하고 믹스를 요구한다.

### 4.2 믹스 두 종류

**LAYERED (기본 권장)**  
1층에서 `CONTRACT`로 버킷을 나눈다 (예: 레이블 40 / 실연자 풀 50 / 신탁 10). 2층에서 실연자 풀만 `STEM_TIME`, `MEMBER_PCT`, 또는 그 가중 믹스로 재안분한다. 계약이 “누구의 몫인가”를 정하고 사용량은 그 안에서만 반영한다.

**WEIGHTED**  
각 베이스가 전 파티 벡터를 만든다(없는 파티는 0). 가중치 합 100%로 선형 결합한다. 쓰지 않는 키 가중치는 0이다. 예: 스템 시간 40 + 멤버 % 30 + 계약 30.

1차와 2차는 서로 다른 정책 버전을 가질 수 있다. 2차 생성 시 1차를 복사한 뒤 수정한다.

### 4.3 객체와 가드

- `SettlementRule` — 3풀 비율, PG, 최소지급, 팬 인센티브. `AllocationPolicy`를 참조.
- `AllocationPolicy` — mode, 베이스 입력, mix.kind, 가중치 또는 레이어, 커버리지 가드.
- `RightsSnapshot` — 사용 스템·초, 멤버 %, 계약 지분, 정책 버전. 정산은 이 사본만 읽는다.

가드: 가중치 합 100%, 계약 지분 합 100%, 멤버 % 합 100%(불일치 시 발행 거부), 청구자 커버리지, 신탁 몫과 포인트 풀 분리.

예외: 배분율·안분 정책 미설정은 적재하되 배치 제외, 환불은 원 스냅샷 역분개, 분쟁은 지급 홀드.

현금 풀과 포인트/크레딧 풀은 혼합하지 않는다.

## 5. 모니터링

세 층: 라이선스 헬스, 정책 준수, 원장·정산. 네 번째 사후 유통(허용 범위 밖 공유)은 법무 티켓.

KPI: 활성 그랜트 수, 스냅샷 커버리지, 정산 완료율, 분쟁 SLA.

원장은 append-only. 분쟁은 스냅샷 + 감사 로그만으로 재현한다.

팬에게는 배분 원칙과 본인 내역만 공개한다.

## 6. 이해관계자 백오피스

같은 API, 다른 질문.

| 포털 | 주 질문 |
| --- | --- |
| SPACE 운영 | 오늘 막힌 발행·정산은 무엇인가 |
| 레이블 | 우리 팩이 어디서 얼마 쓰였는가 |
| 아티스트 | 내 음성이 몇 %로 몇 건인가 |
| 신탁·출판 | 곡·횟수·전송량 대사가 맞는가 |
| 재무·법무 | 지급·세금·분쟁이 닫혔는가 |
| 팬 | 이 조합을 내 것으로 가져도 되는가 |

권한: 본인 파티/IP 기본, 직무 분리(룰 편집 ≠ 배치 확정), 스냅샷과 현재 계약을 화면에 섞지 않음, 팬 PII 집계/토큰화.

구축 순서: 도메인 고정 → SPACE MVP → 빌더=그랜트 실시간 검증 → 레이블·아티스트 포털 → 2차 시장·신탁 파일.

## 7. 가정과 미결

가정: 한국 팬덤 캠페인 우선, 외부 상업 유통 기본 금지, 팬은 공동저작권자 아님.

안분 설계 확정본: `안분정책_AllocationPolicy_설계.md`  
물리/논리 모델: `데이터모델.md`

- 기본 템플릿 `VC-ALLOC-DEFAULT-V1`: 계층 믹스, 1층 계약, 2층 실연자 풀 = 멤버 %, 스템 시간은 배정 구간 초.
- 단독·가중 믹스·2층 스템 시간은 IP 오버라이드.
- 정산은 발행 스냅샷의 레시피만 사용.
